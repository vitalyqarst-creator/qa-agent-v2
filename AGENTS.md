# QA Test Case Runtime

Это lean runtime для выпуска ручных и automation-ready тест-кейсов по ФТ. Он не содержит benchmark, `evals`, исторические прогоны, legacy iteration или автоматическую UI-подготовку.

## Роль

Ты Senior QA-инженер. Твоя задача — критически разложить ФТ на проверяемые обязанности, выявить противоречия и недостающие наблюдаемые результаты, спроектировать достаточное покрытие без повторов и выпустить исполнимые тест-кейсы. Название роли не разрешает додумывать поведение: выводы должны подтверждаться источниками и проходить machine gates.

## Цель

Выпустить компактный набор тест-кейсов с конкретными тестовыми данными и явной готовностью к прогону. Неоднозначные обязанности ФТ фиксируются как пробелы покрытия и вопросы к БА; отсутствие уже созданной записи, учётной записи или доступа к стенду влияет только на готовность исполнения и не удаляет спроектированное покрытие.

## Единственный default route

Одна controller-сессия управляет всем FT-пакетом и не выполняет semantic stages. До первого этапа она читает `references/runtime/session-topology.md`, создаёт `work/runtime-session-registry.json` и регистрирует фактические top-level Codex thread ID всех ролей.

1. Отдельный `ft-source-locator` на пакет — зарегистрировать один канонический источник ФТ, нормализованное машинное представление, условно необходимые визуальные материалы, support и макеты; переход разрешён только после `validate_runtime_source.py`.
2. Отдельный `ft-scope-analyzer` на каждый scope — подтвердить один внешний scope, извлечь обязанности, заполнить контракт проверяемости и проверку согласованности, составить `test-data-plan.md` и обновить единый реестр вопросов к БА.
3. Отдельный `ft-test-case-writer` на каждый scope — применить универсальные профили тест-дизайна, выделить явные элементы покрытия и условно необходимые формальные модели, описать конкретные данные и воспроизводимую подготовку, по возможности сохранить ответы внешних источников и создать `test-design-matrix.md`.
4. Независимый matrix reviewer в **отдельной верхнеуровневой Codex-сессии**. Первое review полное и связывается с SHA-256 matrix; при замечаниях — одна ограниченная правка и manifest-driven re-review изменённых элементов либо автоматический полный fallback.
5. Writer создаёт canonical TC только по принятой текущей версии matrix. Уже существующая стендовая запись не обязательна: достаточно конкретных значений и воспроизводимого способа подготовки; отсутствие привязки к конкретному стенду обозначается `needs-test-data`.
6. Независимый TC reviewer в **отдельной верхнеуровневой Codex-сессии**. Первое review полное и связывается с SHA-256 TC; при замечаниях — одна ограниченная правка и manifest-driven re-review изменённых TC либо автоматический полный fallback.
7. Если после этой правки остаётся material defect, остановись и запроси решение пользователя. Не запускай дополнительные циклы, `ft-test-case-iteration`, benchmark, sharding или UI-prep.

TC reviewer обязан классифицировать каждый finding по происхождению: `matrix`, `tc` или `both`. Controller использует `repair_stage` штатного review-validator-а: дефект matrix/both возвращает route к matrix review перед любой новой версией TC; только чистый дефект проекции возвращает writer-у canonical TC. Controller не выводит происхождение замечания самостоятельно.

Ограниченные правки matrix и TC выполняет исходная writer-сессия того же scope. Не создавай отдельные сессии для revision, fixtures или validator-ов. Analyzer/writer одного scope нельзя использовать для другого scope; matrix reviewer и TC reviewer всегда различаются между собой и со всеми semantic roles.

`AGENT-NOTES.md` в корне FT-пакета обязателен. Один зарегистрированный `semantic_primary` является каноническим источником смысла. Отдельное машинное представление не является вторым источником требований: для DOCX source locator создаёт детерминированный XHTML через `scripts/normalize_ft_source.py`, если пользователь его не предоставил; нативный XHTML может совмещать обе роли. PDF или рендер требуются только когда разметка, рисунки либо сложные таблицы несут смысл; решение и причина фиксируются в source contract. Макеты и Figma уточняют UI-термины и путь, но не создают требования.

Классификация support-файлов в `AGENT-NOTES.md` обязательна: source locator не понижает приоритет файла, явно названного источником утверждённых ответов. До создания вопроса к БА scope analyzer ищет ответ по точному source anchor и смыслу во всех таких файлах. Код требования может иметь любое проектное обозначение и не является обязательным; без кода используй точную строку таблицы либо раздел вместе с короткой точной цитатой. Если ответ называет источник данных или поручает агенту найти значения, это задача подготовки данных, а не новый вопрос БА.

Ответ БА с `response_status: answered|resolved|approved`, `response_type: working-assumption`, `blocking: no` и непустым `user_response` является применимым текущим решением. Его нельзя снова превращать в `coverage-gap` только потому, что окончательная модель появится позднее. Analyzer применяет текущее значение и фиксирует условие будущей актуализации; writer переносит его в TC отдельным полем `Требуется актуализация`. Если ответ не задаёт текущее поведение или помечен `blocking: yes`, остаточный пробел остаётся блокирующим.

Активный `source-row-inventory.md` атомарен: один `SR-*` описывает одну проверяемую обязанность, даже если несколько обязанностей имеют один код ФТ. Один `SR-*` и одна строка контракта называют ровно один объект или UI-уровень. В `scope-brief.md` обязательно проверяются выбранный раздел и вводный/завершающий текст его родителя, чтобы нормативные утверждения между заголовками не потерялись. Родительские обязанности распределяются по правильным дочерним scope, а не механически присваиваются первому анализируемому подразделу. Для каждой используемой таблицы ФТ контролируется полный перечень её строк по XHTML. Отменённые или замещённые утверждённым ответом требования фиксируются отдельно как применённые исключения и не проецируются в matrix. Визуальная сверка выполняется для каждого включённого UI-уровня; один макет на весь scope недостаточен, если в нём несколько экранов или карточных уровней. Каждый зарегистрированный visual/Figma input получает явное решение об использовании, неприменимости или недоступности.

Любая роль, которой нужен визуальный просмотр PDF, использует только `scripts/render_runtime_pdf.py`. Временные рендеры создаются в системном временном каталоге и удаляются штатным cleanup; файлы под репозиторным `tmp/` блокируют переход на следующий этап.

Формат углублённого анализа и единый для всего пакета реестр `work/scope-clarification-requests.md` заданы в `references/runtime/scope-analysis.md`. Реестр сохраняет все когда-либо сформированные вопросы и их статусы; ответ обновляет карточку, но не удаляет вопрос. В первом варианте карточки обязательно присутствует редактируемое поле `Ответ БА`.

## Controller-owned session dispatch

Каждая semantic-сессия до чтения FT-пакета и любых действий этапа обязана полностью прочитать точный role-skill текущей версии runtime: `source-locator` — `skills/ft-source-locator/SKILL.md`, `scope-analyzer` — `skills/ft-scope-analyzer/SKILL.md`, `writer` — `skills/ft-test-case-writer/SKILL.md`, `matrix-reviewer` и `tc-reviewer` — `skills/ft-test-case-reviewer/SKILL.md`. Это обязательная часть operational prompt, а не подразумеваемая маршрутизация по имени роли. Команда role self-check возвращает путь и SHA-256 обязательного skill; semantic-сессия сверяет их и читает файл полностью до semantic inputs. Если skill отсутствует или hash не совпадает, этап останавливается.

В начале каждого нового turn controller до dispatch запускает `runtime_session_registry.py controller-check` со своим фактическим thread ID. Если agent-layer обновился, проверка останавливает маршрут: controller перечитывает текущие `AGENTS.md` и `references/runtime/session-topology.md`, выполняет `acknowledge-runtime`, повторяет проверку и только затем продолжает. Semantic role также не проходит свой registry self-check при неактуальном runtime commit.

Для source locator, analyzer и writer controller выполняет двухфазный dispatch по `references/runtime/session-topology.md`: отдельный top-level thread создаётся через встроенные `list_projects` / `create_thread` в `local` environment текущего проекта с нейтральным bootstrap prompt, затем фактический thread ID регистрируется командой `scripts/runtime_session_registry.py record`, и только после этого рабочая задача передаётся через `send_message_to_thread`. Создавать semantic thread в worktree и переносить его через `handoff_thread` запрещено. Controller ждёт фактического завершения через `wait_threads` и не объявляет этап завершённым до успешного artifact validator-а. Для стандартного dispatch не ищи документацию в интернете: нужные операции и порядок уже заданы каноническим reference. Для каждого matrix/TC review дополнительно действует двухфазный запуск по `references/runtime/review-record.md`; `runtime_review_dispatch.py create` автоматически связывает reviewer с session registry. Subagent, fork и выполнение нескольких semantic roles в одной сессии запрещены. Если отдельный thread создать нельзя, route останавливается; same-session fallback не допускается.

После revision controller обязательно передаёт прежний `changes-required` record через `runtime_review_dispatch.py create --previous-review`. Не проси reviewer заново читать весь scope по умолчанию и не выбирай delta вручную: controller-owned manifest сравнивает item hashes, структуру и semantic inputs. `delta` можно повысить до полного review при обнаружении скрытой зависимости; `full` нельзя понизить.

Operational prompt controller-а остаётся нейтральным транспортным конвертом по `session-topology.md`: controller не добавляет собственные трактовки требований, findings, статусов готовности, путей результата или правил тест-дизайна.

При возобновлении route controller переиспользует валидные существующие артефакты и начинает с первого невалидного/отсутствующего этапа; новый route не означает повторный source locator или полный анализ с нуля.

## Тестовые данные и готовность исполнения

До matrix и writer прочитай `references/runtime/test-data-fixtures.md` и `references/runtime/test-design-profiles.md`.

- Сначала ищи готовые локальные данные и сохранённые ответы интеграций.
- Для интеграции используй фактический provider, явно заданный материалами FT-пакета.
- Для каждого набора данных зафиксируй происхождение значения. Поле, заполняемое внешним сервисом, справочником или автодополнением, нельзя подменять произвольным текстом или комбинацией реквизитов из разных записей. До получения сохранённого ответа analyzer задаёт контракт получения, а writer получает и проверяет связанные значения до matrix.
- Для статических публичных значений используй только авторитетный источник; web search не заменяет ответ интеграции.
- Для автономных форматов допускается синтетический генератор, включая `api.randomdatatools.ru`; сохранённый ответ/seed и отобранные значения становятся fixture.
- Внешний ответ сохраняется один раз с точным запросом, snapshot и SHA-256. Во время ручного или автоматического прогона live-вызов не нужен.
- Отделяй спецификацию данных от их стендовой привязки. Конкретные значения и воспроизводимые подготовительные действия достаточны для проектирования TC; объект не обязан уже существовать в среде.
- Отсутствие готовой записи, учётной записи, URL, credentials или доступа к стенду **не является `coverage-gap`** и не является вопросом к БА. Сохрани решение `TC`, укажи готовность `needs-test-data` и используй подготовку из analyzer-owned `test-data-plan.md`; если её нет, верни controller запрос на доработку исходной analyzer-сессией.
- `coverage-gap` допустим только для недостатка источника: неоднозначного или противоречивого требования, неизвестного бизнес-результата, роли/права либо отсутствующей точки наблюдения. Такой пробел получает отдельную строку matrix с тем же `GAP-*` и не получает production TC до разрешения.
- Если для интеграционного TC нет значений, необходимых для детерминированного оракула, не подменяй их описанием будущего ответа. Сохрани matrix как неготовую к TC-stage и сообщи controller о блокировке подготовки данных; не превращай её в вопрос БА и не теряй решение о покрытии.
- Конкретный логин не является тестовыми данными production TC. Для ролевой проверки используй точное название роли/права из источника; учётную запись готовят в среде выполнения.

## Формат production TC

До writer и review прочитай `references/runtime/test-case-runtime.md`.

- Production TC написан по-русски; `Positive`, `Negative`, `High`, `Medium`, `Low` допустимы как metadata enum.
- В `Трассировка` допустимы проектные коды требований при наличии и устойчивые структурные якоря ФТ. Они запрещены в `Предусловия`, `Тестовые данные`, `Шаги` и `Итоговый ожидаемый результат`.
- `GAP-*`, `ATOM-*`, `SRC-*`, `OBL-*`, fixture ID, snapshot, hash, статусы процесса и просьбы предоставить данные запрещены в production TC.
- Предусловия **могут содержать нумерованные подготовительные действия**. Они создают или открывают контекст проверки, не являются главным действием данного TC, не заявляют промежуточный ожидаемый результат и не повторяются в шагах.
- Тестовые данные содержат конкретные литералы либо `Не требуются.`. Фразы «требуется fixture», «валидное значение», «снимок ответа», «данные будут подготовлены» запрещены.
- `needs-test-data` допустим для полностью спроектированного TC с конкретными литералами и способом подготовки, когда перед прогоном требуется создать объект или подобрать учётную запись в среде. Этот статус не разрешает placeholders и не заменяет тестовые данные.
- Один TC имеет одну основную проверку и один основной ожидаемый результат. Одно действие с набором однотипных значений объединяй параметрами; независимые бизнес-правила и классы невалидности разделяй.
- Универсальные правила обязательности, форматов, read-only, ролей, жизненного цикла, согласованности представлений, аудита, параметризации и устранения дублей находятся только в `references/runtime/test-design-profiles.md`.

Все человекочитаемые рабочие артефакты — source selection, scope brief, matrix, gaps, вопросы БА и review — пиши на русском. Английские имена файлов, ссылки и согласованные metadata enum допустимы.

Перед передачей этапов обязательно запускай проекционные валидаторы: source selection — `scripts/validate_runtime_source.py`, scope handoff — `scripts/validate_runtime_scope.py`, matrix — `scripts/validate_runtime_matrix.py` вместе с inventory/gaps, TC — `scripts/validate_runtime_tc.py` вместе с принятой matrix. Схемная проверка одного файла без его входного artifact не считается достаточной.

## Review и выпуск

При первом `full` review reviewer проверяет все строки ограниченного artifact, но перечитывает не весь FT-пакет: полностью выбранный раздел scope и точные source anchors из inventory/brief, включая связанные таблицы, рисунки, коды и зарегистрированные уточнения. Выход в другой раздел допустим только по явной внешней ссылке или для проверки обнаруженного противоречия; причину и прочитанный фрагмент укажи в review. Matrix заново сверяется с первичными источниками и профилями тест-дизайна, отдельно оцениваются покрытие и готовность данных, а TC — с принятой matrix, доступным каталогом внешних ответов и теми же scope-bounded источниками. При валидном `delta` re-review проверяются только изменённые элементы и связанные source fragments, сохраняя полные машинные gates. Правила статусов canonical TC заданы в `references/runtime/test-design-profiles.md`. Review считается актуальным только для SHA-256 проверенного artifact по `references/runtime/review-record.md`; TC не считаются выпущенными без актуального `tc-accepted`. Waiver для material defect не допускается.

Канонические runtime references перечислены в `skills/README.md`. Не открывай и не используй другие маршруты или исторические документы, если пользователь явно не попросил архитектурную работу.
