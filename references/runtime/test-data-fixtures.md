# Подготовка тестовых данных

## Назначение

Этот этап выполняется до matrix. Его результат — спецификация конкретных значений и воспроизводимой подготовки, а для внешней интеграции по возможности сохранённый ответ provider-а. Уже существующая запись в конкретном стенде не обязательна для проектирования TC.

Различай три сущности:

- **спецификация данных** — tester-facing литералы и способ привести объект к исходному состоянию;
- **сохранённый внешний ответ** — snapshot provider-а, если точные связанные значения зависят от интеграции;
- **стендовая привязка** — конкретная запись, учётная запись и URL среды перед прогоном.

Отсутствие стендовой привязки даёт `needs-test-data`, но не создаёт пробел требования.

## Значения, создаваемые системой

Системный ID, номер, timestamp, sequence или другое значение, которое появляется только после подготовки либо целевого действия, не является заранее известным входным литералом. Не выдумывай его и не блокируй выпуск только из-за отсутствия значения до прогона.

Выбери один из двух проверяемых контрактов:

- **свойство результата** — проверяй наличие, формат, уникальность, монотонность или другую source-backed характеристику, если точное значение не требуется источником;
- **runtime binding** — в воспроизводимом предусловии или шаге явно зафиксируй наблюдаемое значение под уникальным именем, например `PARTNER-ID-01`, и сравни с этим же именем в последующем oracle, если требуется согласованность представлений.

Runtime binding допустим только при указанной точке получения и конкретно идентифицированном объекте. Фраза «ID зафиксирован в протоколе текущего прогона» без действия фиксации и имени значения не является binding. Сам binding не переносится в список входных литералов как будто его значение известно заранее.

Если источник требует конкретное значение, property-check или binding не заменяют отсутствующий литерал. Если значение выдаётся системой и доступно при подготовке на стенде, готовность остаётся `needs-test-data`, а не `blocked-data-preparation`. Последний статус применяй только когда отсутствует необходимый вход и его нельзя получить разрешённым механизмом.

## План данных analyzer-а

Если специальные данные нужны, `test-data-plan.md` содержит таблицу:

| Группа проверок | Источник значений | Данные или контракт получения | Воспроизводимая подготовка | Границы и классы | Готовность |
| --- | --- | --- | --- | --- | --- |

Допустимые источники значений: `первичный источник`, `утверждённый ответ БА`, `сохранённый ответ`, `внешний сервис: <название>`, `проектный справочник`, `официальный публичный источник`, `синтетический генератор`, `стендовая подготовка`, `не требуются`. Несколько применимых источников разделяй точкой с запятой.

Для внешнего сервиса без сохранённого ответа в колонке данных укажи `Контракт получения:` с точным запросом или правилом поиска, видом объекта и перечнем полей, которые writer должен сохранить вместе. Готовность такой строки — `требуется получение данных`. Не указывай предполагаемые значения ответа как свершившийся факт. После получения сохранённого ответа writer использует только согласованный набор связанных значений одной записи.

В колонке `Границы и классы` для количественного ограничения укажи `Шаг представления: ...; валидная граница: ...; ближайшее недопустимое: ...; Основание границы: ...`. Основание содержит точный код требования либо точную строку таблицы/утверждённый ответ, действительно задающий предел. Используй точное предельное значение и минимально отличающееся представимое значение за пределом, а не произвольное большое превышение. Если шаг, единица, точность или правило пересчёта не позволяют вычислить ближайшее значение однозначно, напиши `Требуется уточнение: GAP-*` и задай source-level вопрос; не выбирай 41 вместо 40 только потому, что это проще подготовить. Для неколичественной группы напиши `Не применимо: <причина>`.

Тип поля сам по себе не задаёт диапазон. Для поля типа `Дата` нельзя использовать границы 1900/1970/9999, ограничения HTML-контрола, СУБД или платформы, если их нет в ФТ либо утверждённом ответе. В таком случае укажи обычный валидный представитель; классы некорректного календарного значения или формата могут проектироваться как `candidate-ui-calibration`, но не выдаются за source-backed min/max.

`Первичный источник` является источником конкретного литерала только тогда, когда сам литерал присутствует в ФТ. Наличие поля или ограничения в ФТ не делает произвольное значение source-backed. Для связанных идентификаторов, адресов и реквизитов внешнего объекта используй одну сохранённую запись фактического provider-а или официальный реестр. Синтетический генератор допустим только для автономных данных формата и не доказывает бизнес-валидность значения во внешней системе.

Если специальные данные действительно не нужны, вместо таблицы допустима строка `Данные не требуются.`.

## Приоритет источников

1. Уже сохранённая локальная fixture текущего FT-пакета.
2. Фактический provider интеграции, явно названный в ФТ.
3. Проектный справочник или официальный публичный источник для статических значений.
4. Синтетический генератор для автономных данных формата: ФИО, телефон, e-mail, свободный текст, даты, уникальные имена. `api.randomdatatools.ru` допустим только в этом пункте.

Web search разрешён только для поиска авторитетного публичного статического источника. Он не заменяет ответ интеграции, стендовую сущность, роль или банковскую проверку.

## External provider fixture

Для интеграции агент обязан создать или найти `work/test-data/<scope>/fixture-catalog.json`.

Каждая запись содержит:

```json
{
  "fixture_id": "FX-PROVIDER-001",
  "purpose": "Подсказка и связанные значения для проверяемой интеграции",
  "source_type": "provider",
  "provider": "<provider из ФТ>",
  "request": {"query": "...", "endpoint": "..."},
  "runtime_data": {"suggestion": "...", "related_value": "..."},
  "snapshot_path": "fixtures/FX-PROVIDER-001.response.json",
  "snapshot_sha256": "<64 hex>",
  "verified_at": "YYYY-MM-DDTHH:MM:SSZ"
}
```

Секреты и токены в catalog/snapshot не записываются. Используй адаптер фактического provider-а, если он есть в runtime. Для DaData доступен `scripts/capture_dadata_fixture.py`; он применяется только когда DaData прямо указан в материалах FT-пакета, использует `DADATA_API_KEY` из окружения и сохраняет token-free snapshot.

```text
python scripts/capture_dadata_fixture.py --kind party --query <запрос> --fixture-id <FX-ID> --purpose <цель> --fixture-root <work/test-data/<scope>/fixtures>
python scripts/validate_fixture_catalog.py <work/test-data/<scope>/fixtures/fixture-catalog.json>
```

Команда выполняет два одинаковых запроса, отказывается сохранять нестабильную выбранную подсказку и добавляет в catalog конкретные поля ответа, которые writer обязан использовать как литералы в TC.

Validator каталога проверяет, что каждое скалярное значение `runtime_data` присутствует в сохранённом ответе provider-а. Поэтому нельзя вручную соединить название, идентификатор, адрес или банковские реквизиты из разных записей.

## Когда данные ещё не подготовлены

Для обычного объекта системы задай точные поля и подготовительные действия создания или смены состояния. Не требуй, чтобы объект уже существовал, и не отправляй владельцу требований просьбу создать запись.

Если отсутствует только стендовая запись, учётная запись, URL, credentials или доступ к среде:

- сохрани в matrix решение `TC`;
- укажи готовность `needs-test-data`;
- используй способ подготовки из analyzer-owned `test-data-plan.md` и перенеси его в предусловия будущего TC; если способ не определён, верни controller запрос на доработку исходной analyzer-сессией;
- не изменяй `coverage-gaps.md` и `scope-clarification-requests.md`.

Если недоступен внешний provider и без его ответа невозможно назвать tester-facing литералы, зафиксируй `blocked-data-preparation` в результате writer-а и останови переход к TC-stage. Это не вопрос БА и не основание терять строку будущего покрытия. Если неизвестен сам требуемый бизнес-результат или точка наблюдения, это уже source-level `coverage-gap`, который создаёт scope analyzer.

Фразы «нужна fixture», «подготовить значение», «запрос будет определён» не являются тестовыми данными.

## Проекция в тест-кейс

В production TC переносятся только tester-facing literals: точный запрос, организация/значение, необходимые реквизиты, исходное состояние и воспроизводимые действия подготовки. `fixture_id`, snapshot path, SHA-256 и provider diagnostics остаются в work-каталоге. `needs-test-data` не разрешает описание будущих данных вместо литералов.

Значение runtime binding не является входным литералом: в TC переносится действие его фиксации, уникальное имя и проверка того же имени. Не заменяй этот контракт ссылкой на внешний протокол.
