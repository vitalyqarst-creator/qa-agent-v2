# Тестовые данные: контракт и материализация

## Назначение

Тестовые данные готовятся в три коротких шага без новой роли или review-сессии:

1. **На scope analysis** analyzer задаёт минимальный baseline: уже очевидные роли, допустимые источники, source-backed ограничения и известные отношения. Он не обязан предугадывать все роли, которые появятся после применения техник тест-дизайна.
2. **Вместе с matrix** writer создаёт полный `work/practical/<scope>/matrix-data-plan.md`: переносит baseline без ослабления источников и добавляет роли/отношения, необходимые выбранным проверкам. Это не отдельный этап и не материализация значений.
3. **После `matrix-accepted`** тот же writer материализует роли полного matrix-плана в точные tester-facing литералы, сохраняет внешние ответы и проверяет результат штатным validator-ом. Только после этого создаются canonical TC.

Различай:

- **логический контракт** — какие объекты/значения нужны и чем они должны совпадать или различаться;
- **материализация** — конкретные литералы, выбранные для принятой matrix;
- **сохранённый внешний ответ** — snapshot provider-а для связного набора значений;
- **стендовая привязка** — конкретная запись, учётная запись и URL среды перед прогоном.

Отсутствие стендовой привязки даёт `needs-test-data`, но не создаёт пробел требования. Невозможность материализовать обязательный вход даёт `blocked-data-preparation` до написания TC, а не вопрос БА.

## Baseline analyzer-а и полный matrix-план writer-а

Если специальные данные нужны, `test-data-plan.md` содержит таблицу:

| Группа проверок | Роли данных | Допустимый источник | Ограничения и отношения | Границы и классы | Воспроизводимая подготовка | Готовность материализации |
| --- | --- | --- | --- | --- | --- | --- |

Роль данных имеет ID `TD-<ПОНЯТНОЕ-ИМЯ>`, например `TD-PARTNER-A` или `TD-FILE-OVER-LIMIT`. Одна роль обозначает один связный объект или одно автономное значение. Включай не только целевую сущность, но и prerequisite/родительские объекты, необходимые для исполнения проверки.

Одна `TD-*` может повторно упоминаться в нескольких строках групп проверок, если один и тот же логический объект нужен нескольким сценариям. Во всех таких строках набор допустимых источников должен совпадать; групповые ограничения дополняют контракт роли, а не переопределяют её. Writer переносит эту роль в полный matrix-план один раз с объединёнными применимыми ограничениями. Разные наборы допустимых источников для одного ID являются конфликтом baseline.

Допустимые источники: `первичный источник`, `утверждённый ответ БА`, `сохранённый ответ`, `внешний сервис: <название>`, `проектный справочник`, `официальный публичный источник`, `синтетический генератор`, `подтверждённая стендовая привязка`, `не требуются`. Несколько допустимых источников разделяй точкой с запятой. `Стендовая подготовка` не является значением колонки источника: это место/способ исполнения, который указывают только в `Воспроизводимая подготовка`. Для `подтверждённой стендовой привязки` в подготовке обязателен `Контракт подтверждения:` с идентификатором, наблюдаемыми атрибутами и требованиями к будущему evidence. `Контракт получения:` требует явно назвать provider, справочник, публичный, сохранённый или утверждённый источник; `первичный источник` допустим только для литерала, действительно приведённого в ФТ.

В `Ограничения и отношения` укажи source-backed условия: обязательные поля роли, одинаковый/разный бизнес-ключ, один/разные родители, уникальность внутри прогона, исходный статус, отсутствие дубля и стратегия reset/изоляции. Для машинно проверяемого отношения используй `REL-*`; его точные стороны writer запишет в materialization. Не подменяй требуемую бизнес-уникальность случайным timestamp.

В `Границы и классы` для количественного ограничения укажи `Шаг представления: ...; валидная граница: ...; ближайшее недопустимое: ...; Основание границы: ...`. Основание содержит точный код требования либо точную строку таблицы/утверждённый ответ, действительно задающий предел. Для неколичественной группы напиши `Не применимо: <причина>`. Тип поля сам по себе не задаёт диапазон.

`Готовность материализации`: `не требуется`, `требуется` или `готово`. Внешний сервис без сохранённого ответа получает `требуется`; в `Воспроизводимая подготовка` укажи `Контракт получения:` с точным запросом, видом объекта и перечнем связанных полей. Analyzer не пишет предполагаемый ответ как факт. Для совместимости validator принимает прежнее размещение контракта в ограничениях, но новый handoff использует только колонку подготовки.

Если специальные данные действительно не нужны, вместо таблицы допустима строка `Данные не требуются.`.

Writer создаёт `matrix-data-plan.md` в том же каталоге, что и matrix. Он использует ту же таблицу и:

- переносит каждую baseline-роль analyzer-а и не добавляет ей источник, которого baseline не разрешал;
- сохраняет все baseline `REL-*`;
- может добавить новые `TD-*`/`REL-*`, выведенные из применённого профиля, например второй исходно отличный бизнес-ключ для конфликта при редактировании;
- замыкает все роли и отношения, на которые ссылается исполнимая matrix.

`matrix-data-plan.md` является окончательным логическим контрактом принятой matrix. Analyzer-owned `test-data-plan.md` после handoff не изменяется.

## Приоритет источников

1. Уже сохранённая локальная fixture текущего FT-пакета.
2. Фактический provider интеграции, явно названный в материалах FT-пакета.
3. Проектный справочник или официальный публичный источник для статических значений.
4. Синтетический генератор для автономных данных формата: ФИО, телефон, e-mail, свободный текст, дата, уникальное свободное наименование. `api.randomdatatools.ru` допустим только в этом пункте.

Web search разрешён только для авторитетного публичного статического источника. Он не заменяет ответ интеграции, стендовую сущность, роль или банковскую проверку.

`Первичный источник` подтверждает конкретный литерал только когда этот литерал действительно приведён в ФТ. Описание поля или формата не делает произвольный пример source-backed. Синтетический генератор создаёт воспроизводимый формат, но не доказывает бизнес-валидность значения во внешнем сервисе или реестре.

Источник наследуется транзитивно. Если partner/банк/адрес в системе выбирается из provider-а или справочника, тот же механизм обязателен и при подготовке родителя либо prerequisite-объекта для другого TC. Синтетический alias и суффикс `RUN-ID` не делают такую сущность валидной. Исключение возможно только при явном source-backed или утверждённом контракте подготовки, который обходит обычный UI/provider.

`source_type` materialization описывает происхождение конкретного tester-facing литерала, а не место, где объект будет подготовлен. Поэтому будущая фраза «подготовить на стенде» не превращает выдуманное наименование или идентификатор в `environment`-данные. Для значения из provider-а/справочника используй соответствующий source type и fixture, а стендовую подготовку опиши отдельно. `environment` совместим только с логическим источником `подтверждённая стендовая привязка` и допустим лишь для уже подтверждённой конкретной binding; она содержит `environment_binding` со статусом `confirmed`, package-relative путём к UTF-8 evidence и его SHA-256. Все значения binding должны присутствовать в evidence. Если подтверждения нет, materialization не получает `completed`: выбери воспроизводимый исходный источник либо верни `blocked-data-preparation`.

Динамический суффикс разрешён только для автономного свободно вводимого поля, у которого источник не ограничивает значение provider-ом, справочником или фиксированным перечнем. Повторяемость provider-bound сценария обеспечивай разными поддерживаемыми ключами, изолированной средой или подтверждённым setup/reset-контрактом.

## Значения, создаваемые системой

Системный ID, номер, timestamp или sequence, появляющийся после действия, не является заранее известным входом. Не выдумывай его. Выбери:

- **проверку свойства** — наличие, формат или другую source-backed характеристику;
- **runtime binding** — зафиксируй значение под уникальным именем и сравни после отдельного перехода либо на независимой поверхности.

Нельзя читать значение из элемента и доказывать корректность того же элемента сравнением с прочитанным значением без промежуточного перехода. Если источник требует точный литерал, property-check/binding не заменяют его.

Если значение выдаётся системой и доступно лишь при подготовке стенда, это `needs-test-data`, а не `blocked-data-preparation`. Последний статус применяй только к обязательному входу, который нельзя получить разрешённым механизмом.

## Materialization после принятия matrix

После актуального `matrix-accepted` writer создаёт:

`work/test-data/<scope>/data-materialization.json`

Минимальный формат:

```json
{
  "schema_version": 1,
  "scope": "<scope>",
  "status": "completed",
  "matrix_path": "work/practical/<scope>/test-design-matrix.md",
  "matrix_sha256": "<64 hex>",
  "fixture_catalog": "work/test-data/<scope>/fixtures/fixture-catalog.json",
  "bindings": [
    {
      "role_id": "TD-PARTNER-A",
      "used_by": ["M-001"],
      "source_type": "provider",
      "source_name": "<provider из FT-пакета>",
      "fixture_id": "FX-PROVIDER-001",
      "values": {"Наименование партнёра": "...", "ИНН": "..."}
    }
  ],
  "relations": [
    {
      "id": "REL-DIFFERENT-INN",
      "used_by": ["M-001"],
      "left": "TD-PARTNER-A.ИНН",
      "operator": "not-equal",
      "right": "TD-PARTNER-B.ИНН"
    }
  ]
}
```

Допустимые `source_type`: `provider`, `dictionary`, `public`, `synthetic`, `environment`, `primary`, `approved-ba`. `used_by` должен точно совпадать со строками принятой matrix, в которых используется роль/отношение. `values` содержит только нужные tester-facing поля, а не весь технический ответ.

Запусти:

```text
python scripts/validate_runtime_test_data.py <data-materialization.json> --matrix <test-design-matrix.md> --data-plan <matrix-data-plan.md>
```

Validator проверяет SHA matrix, полноту ролей/отношений, совместимость источника, связи `equal`/`not-equal`, отсутствие placeholders и соответствие provider-bound значений сохранённой fixture. Если matrix не использует `TD-*`/`REL-*`, materialization-файл не обязателен.

## External provider fixture

Для provider writer создаёт или переиспользует `work/test-data/<scope>/fixtures/fixture-catalog.json`. Каждая запись содержит `fixture_id`, назначение, provider/request, выбранные `runtime_data`, путь и SHA-256 token-free snapshot. Секреты не сохраняются.

Для DaData доступен package-specific адаптер `scripts/capture_dadata_fixture.py`; применяй его только когда DaData прямо указан в материалах FT-пакета:

```text
python scripts/capture_dadata_fixture.py --kind party --query <запрос> --fixture-id <FX-ID> --purpose <цель> --fixture-root <work/test-data/<scope>/fixtures>
python scripts/validate_fixture_catalog.py <work/test-data/<scope>/fixtures/fixture-catalog.json>
```

Универсальный runtime не предполагает конкретный provider. Если для provider-а нет адаптера, получи ответ разрешённым read-only способом, сохрани token-free snapshot и catalog того же контракта.

## Проекция в TC

В production TC переносятся только конкретные tester-facing литералы, исходные состояния и воспроизводимые действия подготовки. `TD-*`, `REL-*`, `fixture_id`, snapshot path, SHA-256 и diagnostics остаются в work-каталоге. `needs-test-data` не разрешает описание будущих данных вместо литералов.

Точные значения одной provider-записи переносятся связно. Не соединяй название, идентификатор, адрес или реквизиты из разных ответов. Внешняя fixture подтверждает связность данных, но не отсутствие дубля в стенде; для create-сценария нужен отдельный контракт изоляции/reset либо другой поддерживаемый ключ.
