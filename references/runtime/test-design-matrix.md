# Компактная матрица тест-дизайна

Матрица — один файл `work/practical/<scope>/test-design-matrix.md`. Она нужна, чтобы до написания TC проверить покрытие и объединение однотипных проверок, а не чтобы создавать дополнительный маршрут.

До создания matrix прочитай `references/runtime/test-design-profiles.md`.

## Обязательные колонки

| ID | Источник требования | Проверка | Профили тест-дизайна | Элемент покрытия | Предусловие/исходное состояние | Тестовые данные и отношения | Ожидаемый результат | Решение | Готовность |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |

- `Источник требования`: один или несколько `SR-*` из `source-row-inventory.md`, затем код ФТ с любым проектным обозначением при наличии. Для требования без кода укажи точную строку таблицы либо раздел вместе с короткой точной цитатой абзаца/элемента списка. `SR-*` не заменяет первичную трассировку.
- `Проверка`: одно пользовательское действие и один основной оракул.
- `Профили тест-дизайна`: применимые профили из `test-design-profiles.md`; минимум `базовый`. Для общего отрицательного пути зависимых обязательных read-only/autofill полей используй `зависимая-обязательность`.
- `Элемент покрытия`: краткий проверяемый source-backed результат; для формальных профилей — один или несколько идентификаторов `EP-*`, `BVA-*`, `DT-R*`, `ST-T*`, `CT-C*`. Для строки пробела используй её `GAP-*`.
- `Тестовые данные и отношения`: `TD-*`/`REL-*` из writer-owned `matrix-data-plan.md`, точные source-backed/coverage-critical литералы либо `Не требуются.`. Writer переносит baseline analyzer-а без ослабления и добавляет роли/отношения, которые возникли при проектировании matrix. До принятия matrix здесь не требуются случайно подобранные provider/environment сущности. Внутренние fixture IDs не используются.
- Системно создаваемое значение не выдавай за входной литерал. В строке matrix выбери и назови один контракт: `проверка свойства: <source-backed свойство>` либо `связывание динамического значения; точка фиксации: <наблюдение>; точка сверки: <другое наблюдение или наблюдение после отдельного перехода>`. Формулировки «ID текущего прогона» и «ID зафиксирован» без такого выбора не являются тест-дизайном.
- `Решение`: `TC` или `coverage-gap`. Решение отвечает только на вопрос, существует ли детерминированная source-backed проверка.
- `Готовность`: для `TC` — `ready`, `needs-test-data` или `candidate-ui-calibration`; для `coverage-gap` — только `blocked-observability`.
- Отсутствие уже созданного объекта, учётной записи, URL, credentials или доступа к стенду не меняет решение `TC`: используй `needs-test-data`. Логические роли бизнес-данных, отношения и воспроизводимая подготовка обязательны; их конкретные литералы появляются в materialization после `matrix-accepted`. Общий актор, URL, логин, credentials, авторизация и доступ к модулю не являются `TD-*`: сохрани их только как предусловие, а при отсутствии иных данных укажи `Не требуются.`.

Если один элемент поиска принимает несколько альтернативных source-backed ключей, например наименование или идентификатор, matrix обязана покрыть каждый ключ либо сохранить точный GAP. При одинаковых пути, событии и oracle объедини варианты одной параметризованной строкой/будущим TC; не создавай дубли.

Источник данных проверяется транзитивно: prerequisite/родительская сущность наследует provider, справочник или иной механизм своей канонической идентичности. Синтетическое значение или `RUN-ID` для provider/dictionary-bound роли — дефект matrix, даже если целевая проверка относится к дочерней сущности.
- Для строки `coverage-gap` значение `ID` совпадает с `GAP-*` из `coverage-gaps.md`, а `Источник требования` содержит ровно ту одну `SR-*`, которая указана в колонке `Связанная обязанность`. Так атомарный пробел нельзя потерять или объединить между этапами.

## Условная модель покрытия

Если хотя бы одна исполнимая строка использует профиль `допустимые-классы`, `границы`, `таблица-решений`, `переход-состояния` или `комбинаторный`, после основной matrix добавь один общий раздел `Модель покрытия`:

| Элемент покрытия | Техника | Параметр или условия | Класс, точка, переход или комбинация | Представитель | Ожидаемый результат | Основание |
| --- | --- | --- | --- | --- | --- | --- |

Допустимые пары идентификатора и техники:

- `EP-*` — `классы-эквивалентности`;
- `BVA-*` — `граничные-значения`;
- `DT-R*` — `таблица-решений`;
- `ST-T*` — `переходы-состояний`;
- `CT-C*` — `комбинаторное-покрытие`.

Таблица содержит только спроектированные проверяемые элементы. Невозможные комбинации или переходы перечисли отдельным коротким списком после неё с основанием исключения; неизвестное основание является `coverage-gap`. Каждый формальный элемент таблицы проецируется ровно в одну строку основной matrix. Несколько элементов допустимо объединить в одной параметризованной строке, если для них совпадают путь, trigger и основной oracle.

### Контроль граничных семейств

Если используется профиль `границы`, после модели покрытия добавь таблицу:

| Семейство границы | Тип границы | Точка ниже | Точка на границе | Точка выше | Ожидаемая допустимость | Основание |
| --- | --- | --- | --- | --- | --- | --- |

Одна строка описывает одну вычислимую границу одного параметра либо условного домена. `Тип границы`: `нижняя`, `верхняя` или `точная`; ожидаемая допустимость соответственно `нет/да/да`, `да/да/нет` или `нет/да/нет`. Три точки — разные `BVA-*`, присутствующие в модели покрытия и спроецированные в основную matrix. Для зависимого домена, например максимального дня разных календарных месяцев, создавай отдельные семейства. Одинаковый UI-путь и oracle по-прежнему объединяй одной параметризованной строкой matrix: таблица контролирует полноту модели, а не число TC.

### Контроль уникальности

Если используется профиль `уникальность-и-дубли`, добавь таблицу:

| Бизнес-ключ и область | Создание дубликата | Самосовпадение при редактировании | Конфликт при редактировании | Тот же ключ, другое неключевое поле | Основание или исключение |
| --- | --- | --- | --- | --- | --- |

В каждой сценарной колонке укажи одну строку `M-*` с профилем `уникальность-и-дубли` либо `Не применимо: <source-backed причина и точный anchor>`. Anchor находится в той же ячейке, а не только в общей колонке основания; отсутствие требования или его механический поиск по выбранному подразделу не доказывает неприменимость. Таблица не создаёт проверки без основания: она вынуждает до review явно решить применимость create/edit-вариантов, области ключа и неключевых атрибутов. Все строки matrix с этим профилем должны присутствовать в контроле.

`coverage-gaps.md` использует таблицу:

| ID | Связанная обязанность | Источник | Класс | Недостаток источника | Что требуется для закрытия |
| --- | --- | --- | --- | --- | --- |

Допустимые классы: `неоднозначность-требования`, `противоречие-источников`, `нет-бизнес-результата`, `нет-точки-наблюдения`. Отсутствие тестовых записей или доступа к среде не относится ни к одному из них.

## Правила объединения и разделения

- Решения об атомарности, параметризации, связанных результатах и независимых классах принимай только по `test-design-profiles.md`.
- Для source-backed ограничения уникальности до подбора примеров определи бизнес-ключ, область уникальности и применимость создания/редактирования; используй профиль `уникальность-и-дубли`.
- Для условно применимой формальной техники сначала создай модель покрытия, затем проецируй её элементы в строки matrix. Нельзя подбирать TC-примеры до определения классов, границ, правил, переходов или комбинаций.
- Перед review проверь каждую строку, которая выполняет или пытается выполнить сохранение: в `Тестовые данные и отношения` должны быть перечислены составная роль проверяемого состояния и все обязательные prerequisite-роли/отношения либо точная source-backed вариация отсутствующего значения. Фразы «корректная карточка» и «остальные обязательные поля заполнены» не являются замкнутым контрактом данных.
- Перед review проверь материализуемость каждого отношения. Нельзя независимо варьировать компоненты одной provider/dictionary-bound идентичности, если provider/справочник не выдаёт требуемую пару, поле не имеет source-backed ручного редактирования и нет утверждённого отдельного канала подготовки. Недостижимая комбинация не становится TC из-за профиля уникальности, таблицы решений или статуса `needs-test-data`.
- Для `зависимая-обязательность` перечисли все покрываемые `SR-*`, один `REL-*` зависимого заполнения и остальные независимые обязательные роли. Не создавай отдельные строки, требующие очистки одного read-only output.
- Для решения `TC` не создавай строку без проверяемого результата или спецификации данных. Стендовая запись может быть подготовлена позже; это отражается в `Готовность`.
- Применяй gate частичной тестируемости до решения `coverage-gap`: отсутствие точности у одной части составного требования не отменяет строки `TC` для остальных детерминированных результатов. GAP должен описывать только неизвестный атом или неизвестную исчерпывающую полноту; он не может поглощать проверяемое открытие экрана, изменение состояния, сохранение либо другой минимальный source-backed oracle.
- Каждая активная обязанность из `source-row-inventory.md` должна присутствовать в матрице через свой `SR-*`. Несколько атомарных строк инвентаря допустимо объединить в одну строку матрицы только по правилам профилей тест-дизайна. Раздел применённых исключений не проецируется в матрицу. Открытый пробел остаётся строкой `coverage-gap`; закрытый хранится только в истории и не проецируется.
- Для каждого нажатия условно доступного контрола колонка `Проверка` содержит его UI-триггер непосредственно перед нажатием. Отдельная строка доступности контрола не считается пререквизитом другой строки.
- Результат вида «объект недоступен» без подтверждённого экрана, списка, контрола, ответа API или иной точки наблюдения не является TC: analyzer обязан представить его как `coverage-gap` класса `нет-точки-наблюдения`.
- Перед review выполни gate достижимости: каждое действие в `Проверка` должно быть доступно указанному актору при заданном исходном состоянии. Если более сильное source-backed ограничение из другой `M-*` строки делает прямую отрицательную проверку невозможной и одновременно доказывает её результат, не планируй действие над невидимым объектом; явно сошлись на покрывающую строку в `Проверка` или `Ожидаемый результат`.
- Сохраняй точную ролевую семантику уже в matrix: если связанная обязанность говорит, что элемент «видим и доступен только» роли, отрицательная ветка должна ожидать отсутствие элемента. Общее «действие недоступно» не считается эквивалентом, потому что допускает видимый disabled-элемент.
- Перед review запусти `python scripts/validate_runtime_matrix.py <matrix> --source-inventory <source-row-inventory.md> --coverage-gaps <coverage-gaps.md>`.

## Writer workflow state

Рядом с matrix создай `work/practical/<scope>/workflow-state.yaml`:

```yaml
role: writer
scope: "<scope>"
matrix_status: review-pending
test_design_matrix: "work/practical/<scope>/test-design-matrix.md"
matrix_sha256: "<SHA-256 текущей matrix>"
matrix_data_plan: "work/practical/<scope>/matrix-data-plan.md"
data_status: not-started
test_case_status: not-started
```

`completed` не является допустимым значением `matrix_status`. Controller штатным helper-ом переводит состояние в `accepted`, `changes-required` или `revision-exhausted`; `accepted` всегда относится к текущему SHA-256 matrix. После выпуска TC writer меняет только `test_case_status` и добавляет `test_cases`. Analyzer-owned `work/stage-handoffs/<scope>/workflow-state.yaml` не изменяется.

Штатные переходы:

```text
python scripts/runtime_workflow_state.py pending --matrix <matrix>
python scripts/runtime_workflow_state.py apply-review --matrix <matrix> --review-record <review.json>
python scripts/runtime_workflow_state.py exhausted --matrix <matrix> --previous-review <review.json> --closure <revision-closure.md>
python scripts/runtime_workflow_state.py validate --matrix <matrix>
```

Writer вызывает `pending` после создания и каждой revision matrix. Controller вызывает `apply-review` только для валидного review-record текущей matrix. `exhausted` допустим лишь после единственной revision при остаточных findings, явно закрытых в closure-отчёте. Перед материализацией и TC controller обязан запустить `validate`; только `accepted` разрешает продолжение.

Если неизменная matrix получает новый полный review после обновления agent-layer, новый валидный record может атомарно заменить прежний по тому же каноническому пути: `apply-review` допускает только ожидаемое расхождение SHA прежнего record и сразу привязывает state к SHA нового. Любая иная ошибка pre-review state остаётся блокирующей.

## Результат review

Reviewer сверяет матрицу с первичными источниками и профилями тест-дизайна, затем выносит только `matrix-accepted` либо `matrix-changes-required`. Review-record связывается с SHA-256 matrix по `references/runtime/review-record.md`. После одной ограниченной правки повторяет review; второй дополнительный цикл не запускается без решения пользователя.
