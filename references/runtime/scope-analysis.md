# Контракт анализа области проверки

Анализатор создаёт проверяемую модель одного раздела, не перечень TC.

## Обязательные артефакты

- `source-row-inventory.md`;
- `scope-brief.md`;
- `coverage-gaps.md`;
- `test-data-plan.md`;
- `prompt.scope-to-writer.md`;
- `workflow-state.yaml` со ссылкой `clarification_register: "work/scope-clarification-requests.md"`.

Initial handoff содержит `scope_revision_count: 0` и `status: draft`. Первая локальная коррекция меняет count на `1`. Если остаются ошибки и validator вернул `correction_allowed=true`, разрешена одна финальная delta-only коррекция с count `2`: только по оставшимся findings, без перечитывания источников и новых смысловых решений. Значение не сбрасывается; ошибка при `2` останавливает этап со status `failed`. Status устанавливает validator.

Перед каждой коррекцией сопоставь каждую ошибку проверки с конкретным изменением и проверь отсутствие прежнего нарушения.

Точные форматы ID, копируемые Markdown-шаблоны, workflow-поля и каталог точных строк XHTML выдаёт `python -X utf8 scripts/validate_runtime_scope.py <package-root> --print-contract --scope <scope>`.

## Границы источника

В `scope-brief.md` используй шаблоны `boundaries` и, при распределении, `parent_ownership` из публичного контракта.

Обязательны `Выбранный раздел`, вводный и завершающий текст родительского раздела. Решение: `Включён`, `Распределён`, `Ранее покрыт: <область>` или `Не применимо: <причина>`.

Диапазон кодов структурного якоря охватывает все кодированные источники активного инвентаря. Для выбранного раздела укажи первый и последний фактические `SR-*` без устаревшего диапазона.

Любой нормативный фрагмент вне выбранного раздела, включая общее ограничение, помечай `Распределён`, а не `Включён`; одна строка ownership — одна обязанность и явная целевая область. В таблице контракта обязательна колонка `| Родительская обязанность |`. При их отсутствии напиши `Нормативные родительские обязанности отсутствуют.`.

## Инвентарь и проверяемость

В `source-row-inventory.md` используй шаблоны `source_inventory` и `verifiability` из публичного контракта.

Каждая `SR-*` встречается один раз и содержит один объект/UI-уровень, действие и результат. Успешный результат и отказ/ошибку разделяй на разные `SR-*`; несколько невалидных классов с одинаковым отказом и сообщением параметризуй в одной негативной обязанности. Альтернативные ключи поиска или способы ввода (`A или B`) сохраняй как отдельные классы данных и явно проводи до matrix. Неизвестная часть не блокирует известную; результат без точки наблюдения получает GAP `нет-точки-наблюдения`.

При удалении или перенумерации `SR-*` во время коррекции найди этот ID во всех файлах текущего handoff и обнови каждую ссылку. Не записывай сплошной диапазон через отсутствующий ID: используй отдельные непрерывные сегменты либо явный список.

Если обязательное поле системно предзаполняется и недоступно для редактирования, не проектируй недостижимое пустое состояние. Покрой непустое предзаполнение и read-only; отдельный негатив допустим только при подтверждённом способе получить пустое значение.

Для активной строки таблицы ссылка на строку — только anchor, а не доказательство полного покрытия. Сопоставь все применимые проверяемые свойства колонок: флаг обязательности, флаг редактируемости, тип/класс ввода и примечание с бизнес-результатом. Независимые свойства получают отдельные `SR-*`; в строке контроля перечисли все связанные ID. Диапазон `SR-001–SR-005` трактуется как полный диапазон, но явный список предпочтительнее при разнородных свойствах.

Прямо связанный рисунок/макет конкретизирует видимые элементы уже заданного бизнес-результата, но не создаёт бизнес-логику. Проверяй подтверждённые элементы; GAP оставляй только на неизвестную полноту.

Для обязательного поля нейтральный результат: объект с пустым полем не сохраняется. Точную UI-реакцию утверждай только по источнику.

Отменённые обязанности перечисли в `Применённые исключения`, без активных `SR-*`/GAP.

## Условные контроли

Создавай контроль только при наличии триггера и повторяй его перед каждым действием.

### Строки таблицы

Если область использует таблицу ФТ, используй шаблон `table_rows`.

Перечисли все строки первого столбца XHTML, копируя их из `source_table_catalog` публичного контракта без ручной транскрипции. Решение: `Включена`, `Передана`, `Не применимо` или `Исключена утверждённым ответом`, с областью/причиной/источником.

Для коротких буквенных заголовков используй шаблон `opaque_headers`.

Значение требует явной легенды или утверждённого support; иначе `Не определено` и GAP.

### Визуальная сверка

Для каждого включённого UI-уровня используй шаблон `visual_crosscheck`.

Указывай зарегистрированный путь/Figma URL, подтверждённые подписи, механику и различия буквально.

Не дублируй реестр locator-а и нерелевантные макеты. Если локального evidence недостаточно и Figma зарегистрирована, используй её один раз либо запиши причину недоступности. Без UI укажи причину отсутствия сверки.

### Проверка согласованности

Для применимых аспектов используй шаблон `consistency`.

Допустимые аспекты: `Идентичность объекта`, `Представления объекта`, `Создание, редактирование и повторное открытие`, `Роли и видимость`, `Статусы и переходы`, `Поля, справочники и внешние источники`, `История изменений и аудит`.

Каждая строка фиксирует вывод и ссылки `SR-*`/`GAP-*`. Неприменимые аспекты пропускаются; повторная сверка выполняется только по skill.

## Пробелы и вопросы

В `coverage-gaps.md` используй шаблон `coverage_gaps`.

GAP связан с одной SR и только её неизвестным остатком. Gate частичной тестируемости требует отдельных SR для известных результатов того же утверждения. Классы: `неоднозначность-требования`, `противоречие-источников`, `нет-бизнес-результата`, `нет-точки-наблюдения`.

Закрытый GAP пометь `Закрыт: <решение>`; не передавай writer. При отмене обязанности удали SR/GAP; история остаётся в реестре.

Единый реестр пакета — `work/scope-clarification-requests.md`. Формат карточки:

```markdown
## CLR-9.3.1-001 — Краткая тема

**Область проверки:** `9.3.1-partner-directory`
**Статус:** `ожидает-ответа`
**Вопрос:** Один однозначный вопрос.
**Основание в ФТ:** Точный source anchor.
**Влияние на покрытие:** Один связанный GAP и неизвестный результат.
**Ответ БА:** _Введите ответ здесь._
```

Статусы: `ожидает-ответа`, `частичный-ответ`, `ответ-получен`, `отменён`. Для частичного ответа добавь `Осталось уточнить`, для support — `Источник ответа`; автор/дата БА не нужны. Вопросы не удаляй и не дублируй. Один вопрос может закрывать несколько GAP только при общем недостающем термине/правиле; перечисли все GAP и anchors.

`working-assumption` с текущим поведением и `blocking: no` временно закрывает GAP; в brief сохрани источник, поведение и условие актуализации. Иной ответ оставляет только точный остаточный пробел.
