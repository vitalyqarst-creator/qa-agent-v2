# Универсальные профили тест-дизайна

Этот файл — канонический источник общих правил покрытия для matrix, writer и reviewer. Профили применяются только когда соответствующее свойство следует из ФТ, утверждённого уточнения или допустимого визуального материала. Они не создают новые бизнес-правила.

## Карта применимости

Для каждой проверяемой обязанности в matrix укажи один или несколько профилей:

- `базовый` — позитивное наблюдаемое поведение без специального ограничения;
- `обязательность` — обязательное поле, выбор или блок;
- `только-чтение` — недоступность ручного изменения;
- `автозаполнение` — одно действие заполняет связанные значения;
- `допустимые-классы` — ограничения символов, формата или типа ввода;
- `границы` — минимум, максимум, точная длина, дата или размер;
- `таблица-решений` — результат зависит от сочетания двух или более независимых условий;
- `комбинаторный` — взаимодействуют три или более параметра, а полный перебор избыточен;
- `справочник` — закрытый перечень или autocomplete;
- `уникальность-и-дубли` — бизнес-ключ, область уникальности и отклонение повторной записи;
- `ролевой-доступ` — различия действий или видимости по ролям/правам;
- `переход-состояния` — изменение статуса и его наблюдаемые последствия;
- `жизненный-цикл-создания` — создание, отмена, повторное открытие и очистка формы;
- `согласованность-представлений` — один объект отображается в нескольких местах;
- `аудит-история` — история или журнал изменений;
- `файл` — загрузка, формат, размер, количество или удаление файла;
- `другой:<краткое название>` — source-backed dimension, которой нет в списке.

Отсутствие специального профиля не означает отсутствие проверки: используй `базовый`. Reviewer заново определяет применимость профилей по источникам и не доверяет тегам writer-а без сверки.

Если элемент доступен только после UI-триггера (hover, раскрытие блока, открытие меню), сохрани этот триггер в строке действия или явно свяжи строку действия со строкой доступности. Он является пререквизитом каждого последующего использования элемента, а не отдельной одноразовой проверкой.

## Обязательность

- Каждое поле/действие, помеченное в источнике как обязательное, получает явное решение: TC или `coverage-gap`.
- Для редактируемого поля проверь заполненное допустимое значение и пустое значение с подтверждённым trigger сохранения/перехода.
- Для справочника или autocomplete отрицательный вариант — отсутствие выбора, а не произвольный текст, если прямой ввод не разрешён.
- Для системно заполненного или read-only поля не выдумывай способ очистки. Проверяй его заполнение через разрешённое исходное действие; отсутствие воспроизводимого пути к пустому состоянию фиксируй как ограничение покрытия.
- Несколько обязательных полей можно объединить в один параметризованный TC, только если UI-путь, trigger и основной oracle одинаковы. Для каждого варианта укажи проверяемое пустое поле и конкретные допустимые значения остальных обязательных полей.
- Если один source-backed выбор одновременно заполняет несколько обязательных зависимых полей, а часть из них после выбора недоступна для редактирования, не требуй недостижимого состояния «пусто только одно зависимое поле». Объедини обязанности в одну строку профиля `зависимая-обязательность`: не выполнять инициирующий выбор, заполнить остальные независимые обязательные поля и проверить общий source-backed отказ сохранения. Такая строка перечисляет все связанные `SR-*` и отношение `REL-*`; отдельные негативные TC нужны только при подтверждённом способе изолировать поле.

## Элементы покрытия и условная модель

- Для каждой строки matrix назови проверяемый элемент покрытия. Для обычной source-backed проверки используй краткое русское описание результата; для формальных техник используй идентификаторы `EP-*`, `BVA-*`, `DT-R*`, `ST-T*` или `CT-C*`.
- Если применён хотя бы один формальный профиль, в том же `test-design-matrix.md` создай единую таблицу `Модель покрытия` по `references/runtime/test-design-matrix.md`. Отдельные файлы по техникам не создавай.
- Каждый формальный элемент модели должен быть связан хотя бы с одной строкой matrix, а каждая ссылка из matrix должна существовать в модели. Одинаковый идентификатор нельзя использовать в нескольких строках: эквивалентные варианты объединяй параметрами в одной строке.
- Reviewer независимо восстанавливает применимые элементы из источников. Наличие тега или строки модели само по себе не доказывает полноту.

## Классы эквивалентности и границы

- Для каждого source-backed ограничения выдели непересекающиеся допустимые и недопустимые классы. Дай каждому классу `EP-*`, укажи представителя и ожидаемое принятие или отклонение. Разделяй классы, способные дать разный дефект; эквивалентные значения одного класса объединяй параметрами.
- Для source-правила «только цифры» обязательны: допустимые цифры, латиница, кириллица, пробел, знак/дефис, точка или запятая как десятичный разделитель, другой спецсимвол. Если задана длина — добавь применимые границы `N-1`, `N`, `N+1` либо min/max и значения непосредственно за ними.
- Для каждой вычислимой границы зафиксируй единицу, включённость и отдельные `BVA-*` точки непосредственно внутри, на границе и непосредственно за ней. Не создавай механически одинаковый набор для поля без source-backed границы.
- Каждую выбранную вычислимую границу внеси в `Контроль граничных семейств` matrix. Для многокомпонентных и зависимых доменов отдельно реши применимость каждой границы компонента; пропуск не заменяй одним произвольным представителем класса.
- Если результат зависит одновременно от нескольких числовых или логических ограничений, используй доменное представление: точки на границе, непосредственно внутри и непосредственно снаружи допустимой области.
- Не выводи точную UI-реакцию из ограничения формата. Если факт принятия/отклонения ясен, но точная подсветка, фильтрация или очистка неизвестна, разрешён `candidate-ui-calibration` с конкретным вводом и trigger. Если неизвестен сам результат принятия/отклонения, создай `coverage-gap`.
- Для даты, числа, размера и длины проверяй только границы, которые можно однозначно вычислить из источника или утверждённого уточнения.

## Таблицы решений

- Применяй профиль `таблица-решений`, когда один результат зависит от сочетания как минимум двух независимых условий. Не подменяй таблицу несколькими случайно выбранными примерами.
- Выдели условия, их source-backed значения и все допустимые правила `DT-R*`. Для каждого правила зафиксируй сочетание условий и один ожидаемый результат.
- Невозможные сочетания не превращай в TC. Перечисли их рядом с моделью и укажи source-backed основание исключения; если основание неизвестно, сохрани пробел покрытия.
- Покрой каждое допустимое правило либо явно зафиксируй согласованное риск-ориентированное сокращение. Правила с одинаковым действием и oracle можно объединить параметрами, но их `DT-R*` остаются перечисленными в элементе покрытия.

## Комбинаторное покрытие

- Применяй профиль `комбинаторный` только при трёх и более независимых факторах, когда взаимодействия значимы, а полный перебор заметно раздувает набор.
- Сначала сократи значения каждого фактора по классам эквивалентности и зафиксируй невозможные сочетания. Затем выбери силу покрытия: pairwise по умолчанию для обычного риска; 3-way — только при подтверждённом высоком риске или известных дефектах взаимодействия.
- Не заявляй pairwise достаточным без основания и не используй случайную выборку как доказательство покрытия. Для каждого `CT-C*` сохрани конкретную комбинацию либо детерминированный список/отчёт генератора, по которому покрытие можно воспроизвести.

## Read-only, автозаполнение и внешние подсказки

- Один выбор записи из подсказок/поиска внешнего источника и проверка всех связанных автозаполненных полей — один TC, если это одно действие и единый результат интеграции.
- Не дроби такую проверку на TC по каждому результирующему полю. Разделяй только поля с самостоятельной бизнес-логикой или независимым trigger/oracle.
- Тот же принцип применяется к обязательности зависимого кластера: одно отсутствие инициирующего выбора и один отказ сохранения покрывают все обязательные read-only outputs этого выбора. Не превращай невозможность очистить один output в отдельный GAP, если общий source-backed отрицательный путь достижим.
- Редактируемость нескольких полей с одинаковым UI-путём и oracle можно проверить одним параметризованным TC. Таблица параметров обязана перечислять каждый вариант явно.
- Название provider-а и способ получения fixture берутся из материалов конкретного FT-пакета. Универсальный agent-layer не предполагает конкретный provider или ручной ввод по умолчанию. Тот же источник наследуют prerequisite/родительские сущности: подготовительный объект не становится синтетическим только из-за того, что его создание находится вне текущего scope.
- Если один control поддерживает несколько альтернативных ключей поиска/ввода, перечисли каждый source-backed ключ как dimension покрытия. Когда путь и oracle одинаковы, используй одну параметризованную строку/TC; когда ключ запускает другую логику или даёт другой результат — раздели проверки.

## Уникальность и дубли

- Сначала выведи из источника бизнес-ключ и область уникальности: глобально, внутри родителя, типа, категории, организации или другого явно заданного контекста. Не подменяй это предположением по UI.
- Минимум покрой точный повтор бизнес-ключа и наблюдаемый бизнес-результат: вторая сущность не создаётся либо существующая сущность не становится дубликатом. Точный текст сообщения проверяй только когда он задан источником.
- Если правило действует между типами или категориями, добавь повтор ключа в другом типе/категории. Если правило ограничено родителем, добавь разрешённый одинаковый ключ у другого родителя; если область уникальности неясна, создай `coverage-gap` вместо догадки.
- Когда поддерживаются и создание, и редактирование, отдельно проверь самосовпадение: сохранение существующего объекта с неизменённым собственным ключом не должно считаться дублем. Изменение ключа на ключ другой существующей сущности проверяется как конфликт, если это следует из правила уникальности. Операции карточки восстанавливай также из родительских/контейнерных таблиц действий; их отсутствие в выбранном подразделе не является source-backed исключением.
- Если источником задано, что уникальность определяется только частью полей, измени хотя бы одно неключевое поле и сохрани тот же ключ. Это доказывает семантику ключа, а не случайное полное равенство записей.
- Нормализацию регистра, пробелов, дефисов, пунктуации, `ё/е` и иных представлений проверяй только при явном правиле источника или утверждённом уточнении. Без него обязательна проверка буквального совпадения, но дополнительные классы не выдумываются.
- Эквивалентные варианты одного правила объединяй параметрами. Не объединяй создание и редактирование, разные области уникальности или разрешённый и запрещённый результат, если они могут независимо пройти или упасть.
- До review заполни условный `Контроль уникальности` matrix: создание дубликата, самосовпадение, конфликт редактирования и тот же ключ с другим неключевым полем получают `M-*` либо точное source-backed `Не применимо`.

## Роли и права

- Используй точное название роли или право из источника. Не придумывай роли, логины и названия тестовых учётных записей.
- Неблокирующее временное решение БА задаёт применимое текущее значение роли/права. Проектируй проверку по нему и добавляй условие будущей актуализации; отсутствие окончательной будущей модели само по себе не является пробелом покрытия.
- В TC достаточно предусловия вида «Войти пользователем с ролью `<роль из ФТ>`» или «без роли `<роль из ФТ>`». Конкретная учётная запись относится к подготовке среды и не записывается в production TC.
- Для разных ожидаемых прав доступа создавай отдельные варианты/TC, если результаты могут независимо пройти или упасть.
- Сохраняй точную семантику ограничения. Если источник говорит, что элемент «видим и доступен только» роли, отрицательная ветка проверяет отсутствие элемента у другой роли; общее «действие недоступно» недостаточно, потому что допускает видимый disabled-элемент. Если источник требует именно disabled-состояние, наоборот, не подменяй его отсутствием.
- Для каждой ролевой проверки сначала докажи достижимость точки наблюдения данным актором в заданном состоянии. Нельзя планировать наведение, клик или проверку элемента на объекте, который по другой active obligation этому актору не показывается.
- Отрицательное ограничение действия может быть покрыто другой строкой matrix, если она source-backed и строго сильнее: например, невидимость самого объекта для роли также исключает доступ к действию на нём. В таком случае не создавай неисполняемый дублирующий TC; в строке действия явно укажи связанную `M-*` строку, которая покрывает отрицательную ветку, а прямую проверку оставь только достижимому актору.

## Переходы состояний

- Если источник задаёт два или более состояния либо перехода, выдели `ST-T*`: исходное состояние, событие, source-backed условие/guard, новое состояние и наблюдаемый результат.
- Минимальное покрытие — все source-backed допустимые переходы. Запрещённые переходы проверяй только когда запрет или ожидаемая реакция следуют из источника; не придумывай их из симметрии модели.
- Для критичного жизненного цикла добавляй последовательность переходов или возврат в исходное состояние только при подтверждённом риске. Один недопустимый переход проверяй одним TC, чтобы предыдущая ошибка не маскировала точку отказа.

## Создание, редактирование, отмена и повторное открытие

- Успешное создание использует уникальный для прогона ключ либо явную очистку/изоляцию. Ответ внешнего provider-а сам по себе не доказывает отсутствие объекта в системе. `RUN-ID` допустим только для автономного свободно вводимого поля; он запрещён для provider-bound или dictionary-bound идентичности.
- Для отмены или закрытия без сохранения итоговый oracle проверяет бизнес-эффект: объект не создан либо изменение не сохранено. Само закрытие формы недостаточно.
- После успешного создания проверь повторное открытие формы нового объекта: значения предыдущего объекта не должны наследоваться, кроме source-backed defaults. Если надёжный oracle начального состояния неизвестен, зафиксируй gap или calibration вместо предположения.
- После редактирования проверяй сохранённое значение после повторного открытия, если источник требует сохранения/отображения изменения.

## Согласованность представлений и аудит

- Если один объект после изменения отображается в карточке, списке, поиске, связанном объекте или документе, проверь согласованность source-backed представлений либо явно зафиксируй неприменимость.
- Если источник требует историю/аудит, проверь наличие записи, тип изменения, изменённое значение и доступные source-backed атрибуты события. Не выдумывай автора, timestamp или внутренний формат.

## Атомарность, параметризация и устранение дублей

- Сигнатура проверки: исходное состояние + trigger + объект проверки + основной oracle + класс параметров.
- Если два TC имеют одинаковую сигнатуру и различаются только эквивалентным значением, объедини их параметрами.
- Ближайшая точка за границей и дополнительный source-backed пример по ту же сторону границы объединяются в один параметризованный класс, если у них одинаковые предусловие, control/trigger и oracle. Разные source anchors или profile tags не обосновывают разделение без отдельного риска, trigger или oracle.
- Одно действие с кластером связанных результатов — один TC. Несколько обязанностей, способных независимо пройти или упасть, — разные TC.
- Не объединяй positive acceptance и negative rejection, разные роли с разным доступом, разные переходы состояния или разные классы риска в один TC.
- В параметризованном TC используй таблицу вариантов. Не повторяй один и тот же ключ тестовых данных несколькими bullet-строками.

## Полнота трассировки

- Каждое самостоятельное утверждение подтверждённого scope получает строку matrix либо явное решение `coverage-gap`.
- Если строка/таблица источника содержит буквенно-цифровые коды требований с любым проектным префиксом и разделителем, сохрани каждый применимый код в `Источник требования` matrix и в `Трассировка` соответствующего TC. Ссылка только на таблицу недостаточна, когда у требований есть коды.
- Код не обязателен. Для требования без кода используй устойчивый структурный якорь: точную строку таблицы либо номер раздела вместе с короткой точной цитатой абзаца/элемента списка. Общая ссылка только на раздел не доказывает трассировку.
- Один код не равен одному TC: разложи независимые обязанности, но не теряй общий набор кодов при объединении связанных результатов одного действия.
- Reviewer восстанавливает перечень утверждений и кодов из первичных источников независимо от matrix writer-а.
- При оценке полноты учитывай source-backed логическое покрытие между строками, но только при явной связи в matrix. Не требуй отдельного взаимодействия для следствия, которое невозможно наблюдать напрямую из-за более сильного ограничения доступа.

## Статусы в canonical FT-first наборе

- Отсутствие поля `Статус исполнения` означает `ready`.
- `needs-test-data` допустим, когда проверка, бизнес-результат, конкретные литералы и способ подготовки однозначны, но перед прогоном требуется создать объект, привести его к состоянию или подобрать учётную запись с указанной source-backed ролью. Конкретные логины и URL в TC не записываются.
- `candidate-ui-calibration` допустим, когда требование и ожидаемый бизнес-результат однозначны, но неизвестна точная форма UI-feedback. TC обязан иметь конкретный ввод, trigger и один невыдуманный oracle; поле `Требуется подтверждение` описывает только UI-деталь.
- `blocked-observability` не публикуется как canonical runtime TC: соответствующая обязанность остаётся в matrix как source-level `coverage-gap`.
- Отсутствие готовой стендовой записи не может переводить проверку в `blocked-observability` или `coverage-gap`.
- Reviewer не блокирует TC только из-за `candidate-ui-calibration`, но блокирует выдуманный oracle, неконкретные данные или неопределённый бизнес-результат.
- Если TC основан на неблокирующем временном решении БА, поле `Требуется актуализация` обязательно и не заменяет `Статус исполнения`.
