# Practical route v1 — короткий production-маршрут

## Назначение

`practical-v1` — default-маршрут для обычного подтверждённого scope ФТ. Его
цель — выпустить качественные и видимые тест-кейсы без процессных артефактов,
которые не улучшают тест-дизайн.

Маршрут сохраняет две независимые проверки, но выполняет их в правильном
порядке: сначала принимается тест-дизайн, затем по принятой матрице пишутся и
проверяются тест-кейсы.

```text
source scope → matrix draft → test-data plan/materialization → independent matrix review
→ one matrix revision (и узкое обновление data plan при необходимости)
→ test cases → independent TC review → one TC revision → baseline
```

`practical-v0.9` остаётся legacy-маршрутом только для уже начатых v0.9 scope
и запускается исключительно по явному запросу пользователя. Не переносить в
v1 его manifests, controller attestations, snapshots, triage, obligations или
повторные scope-анализы.

Одна полная доработка после каждого review — предел для изменения тест-дизайна.
После проверки закрытия допускается только один `micro-closure`: локальная
правка уже найденной неточности, не меняющая покрываемое поведение, границы
сценария, основной oracle, статус исполнения, зависимости данных или состав
кейсов. Это не вторая design-revision. Новый finding или сохраняющийся
содержательный defect завершает соответствующую review-фазу как
`review-failed`.

## Входы

- выбранный внешний scope и границы раздела ФТ;
- DOCX и соответствующий XHTML основного ФТ;
- доступные PDF, макеты или Figma — только как визуальные источники; для Figma
  достаточно ссылки на файл или названия страницы/фрейма, `node-id` необязателен;
- `AGENT-NOTES.md`, support-файлы, утверждённые ответы БА и справочники, если
  они есть в FT-пакете.

DOCX задаёт бизнес-требования, XHTML — машиночитаемую структуру. PDF и Figma
уточняют название, расположение и видимость UI-элемента, но не меняют
бизнес-правило. Утверждённый ответ БА имеет приоритет над ФТ в явно указанной
области применения.

Жёстко остановиться можно только если нельзя прочитать основной источник или
невозможно установить границы scope. Не останавливай весь scope из-за
отсутствия UI, роли, fixture, наблюдаемого признака или ответа БА: отрази это
вопросом и честным execution status затронутой проверки.

## Минимальные артефакты

Все рабочие артефакты scope находятся в
`fts/<domain>/<ft>/work/practical-v1/<scope-slug>/`:

- `source-scope.md` — компактная граница scope, источники, source refs,
  применимые решения БА и подтверждённые visual bindings;
- `scope-clarification-requests.md` — всегда создаётся; при отсутствии
  вопросов содержит явную строку «Вопросов к БА не выявлено»; для каждого
  вопроса используй [краткий формат вопросов БА](practical-v1-clarification-requests-format.md);
- `test-design-matrix.md`;
- `test-data-source-plan.json` и `fixture-catalog.md`, если хотя бы одна
  строка matrix зависит от provider-а, синтетического значения, файла или
  состояния среды;
- `matrix-review.md` и, при наличии замечаний, `matrix-revision.md`;
- `test-cases-review.md` и, при наличии замечаний, `test-cases-revision.md`.

Сам набор тест-кейсов создаётся сразу в
`fts/<domain>/<ft>/test-cases/<section-id>-<scope-slug>.md`. До завершения
review в заголовке файла указан статус `draft`; после принятия он меняется на
`baseline`. Пользователь всегда видит актуальный набор по привычному пути.

Не создавай `workflow-state`, immutable manifest, attestation, dispatch
receipt, snapshot, OBL/CTX/SETUP ledger, отдельный source-parity artifact или
процессные debug-файлы. Если PDF сверялся с DOCX/XHTML, кратко отрази вывод в
`source-scope.md`.

## 1. Source scope и вопросы БА

Создай `source-scope.md` с разделами:

1. `Границы scope` — разделы, таблицы, рисунки и исключения;
2. `Источники и приоритет` — фактически использованные файлы;
3. `Требования` — одна строка на независимое утверждение: код требования при
   наличии, source locator, короткое утверждение на русском. Для поля scope
   включай относящиеся к нему глобальные правила типа данных: формат, диапазон,
   календарную валидность, длину или иной общий constraint;
4. `Визуальные уточнения` — только подтверждённые рисунком/PDF/Figma названия
   или расположение контролов;
5. `Решения БА` — ID/краткий ответ/область применения;
6. `Ограничения исполнения` — только конкретные отсутствующие данные, UI или
   наблюдаемые результаты.

Если в пакете зарегистрирована Figma-ссылка, релевантная выбранному scope,
один раз выполни её визуальную проверку до матрицы. Сначала используй указанный
`node-id`, если он есть; иначе сам найди страницу или фрейм по названиям scope,
экрана, действия или элемента из ФТ/локального макета. Не проси пользователя
сначала сообщить `node-id`. В подразделе `Визуальные уточнения` кратко запиши
`figma_id`, просмотренную страницу/фрейм, известный `node-id` при его наличии
и один итог: `checked-and-used`, `checked-no-new-information`, `unavailable`
или `not-relevant`. После анализа релевантной Figma-записи не оставляй
`not_checked`. Недоступность Figma, несколько неразличимых кандидатов или
отсутствие подходящего фрейма не блокируют scope: зафиксируй итог и продолжай
по ФТ/PDF/локальному макету. Figma уточняет только UI-шаги; бизнес-правило
по-прежнему выводится из ФТ или утверждённого ответа БА.

До матрицы сформируй `scope-clarification-requests.md`. Вопрос задаётся, лишь
если ответ изменит ожидаемый бизнес-результат, состав тестовых данных, ветку
сценария или применимость требования. Один корневой вопрос объединяет все
затронутые проверки. Вопрос содержит source ref, почему он влияет на тест и
область применения ответа. В каждой карточке `BAQ-*` оставь поля `Статус`,
`Ответ БА` и `Решение для тест-дизайна`; ручной текст ответа не перезаписывай
при повторной материализации scope.

## 2. Матрица тест-дизайна

Writer создаёт русскоязычную `test-design-matrix.md`. Каждая строка описывает
test intent, а не технический шаг. Обязательные столбцы:

| ID идеи | Требование и источник | Проверка | Техника | Основной ожидаемый результат | Данные/состояние | Статус исполнения | Вопрос/решение БА |
| --- | --- | --- | --- | --- | --- | --- | --- |

Перед matrix review writer сам проверяет:

- каждое независимое утверждение ФТ имеет строку матрицы или явный gap;
- разные business result, ветка, исходное состояние или реакция не склеены;
- эквивалентные значения одного контрола с одной реакцией параметризованы,
  а не искусственно раздроблены;
- для создания есть исходное отсутствие, бизнес-ключ и очистка; для отмены и
  закрытия — oracle отсутствия сохранения;
- для format/boundary требований перечислены применимые классы;
- для явного ограничения перечислены граница и соседний недопустимый класс;
  для ограничения уникальности — применимость внутри и вне заданного
  владельца/контекста; для множественного выбора — один и несколько элементов;
  для документированных способов поиска — каждый способ. Не добавляй класс,
  если он не следует из источника;
- если ФТ называет создание, редактирование, сохранение, отмену или закрытие,
  matrix содержит отдельный результат для применимых entry-state: создание и
  его наблюдаемое сохранение, редактирование и повторное открытие, отмена
  создания и отмена изменения. Объединение допустимо только при одинаковых
  исходном состоянии, действии и oracle;
- нет вымышленных UI-реакций, ролей, учётных записей и fixtures;
- коды требований из `source-scope.md`, включая коды из таблиц, перенесены в
  matrix и далее в трассировку покрывающего TC; непокрытый код остаётся с
  точным `GAP-*`, а не исчезает из набора;
- повторные test intent помечены как дубли или обоснованно объединены.
- каждая корректная test-строка данных не нарушает другое применимое
  source-правило, а каждый невалидный класс выведен из источника;
- основной oracle наблюдаем; внутренний статус без наблюдаемого проявления
  вынесен в gap или соответствующий execution status;
- для save/cancel подготовлены все зависимые обязательные данные, а не только
  поле, на котором сосредоточена проверка;
- у параметризованной строки явно записано, почему варианты имеют одно
  действие и одну реакцию.

## 3. Планирование и материализация тестовых данных

После self-check черновика matrix controller определяет, нужны ли внешние,
синтетические, файловые или стендовые данные. Если нужны, он до matrix review
создаёт и проверяет `test-data-source-plan.json` и `fixture-catalog.md` по
[политике источников тестовых данных](test-data-source-planning-policy.md).
Это один короткий pre-review gate, а не отдельный review-цикл.

Для каждого provider-backed свойства plan содержит точный component path и
проверенное literal-значение. Перед сохранением fixture controller сверяет
семантику provider-а: отсутствие точного свойства, например отдельного
фактического адреса у ответа организации, создаёт/дополняет `BAQ-*` или
`GAP-*` и переводит только затронутую зависимость в `blocked`. Юридический
адрес, случайное имя или сходное поле не подменяют отсутствующее свойство.

Для требований к файлам controller использует локальный generator с размером
в байтах. Не создавай «40 МБ» fixture, пока источник или БА не определили
точное количество байт. Для роли, состояния объекта или его отсутствия plan
фиксирует точную требуемую подготовку и очистку, но не выдумывает логин,
URL, пользователя или ID объекта.

Matrix reviewer получает matrix вместе с plan и catalog. Если matrix не
содержит data-dependent строк, в scope достаточно краткой отметки
`test-data plan: not required`.

## 4. Независимое matrix review

Matrix review проводит отдельная верхнеуровневая Codex-сессия, не subagent и
не writer. Reviewer использует `source-scope.md` как навигацию, но независимо
проверяет каждый релевантный source locator в DOCX/XHTML и связанные глобальные
правила типа данных. Он не перечитывает весь пакет без причины: расширяет
выборку только при cross-reference или признаке противоречия. ID reviewer
сессии передаётся в задаче review; reviewer не ищет другие Codex-задачи и не
собирает их историю.

Reviewer возвращает короткий `matrix-review.md`:

- ID отдельной reviewer-сессии;
- verdict: `matrix-accepted` или `matrix-changes-required`;
- нумерованные findings с source ref, серьёзностью и точным требуемым
  исправлением;
- явную проверку покрытия, атомарности, смысловых дублей, классов данных,
  lifecycle create/edit/cancel, границ/контекстов и вопросов БА;
- для релевантной Figma — что выполнена визуальная проверка либо честно
  зафиксирована её недоступность; reviewer не принимает `not_checked` и
  проверяет, что Figma не использована как источник бизнес-правила;
- сверку множества кодов `source-scope.md` с matrix: каждый код покрыт строкой
  или точным `GAP-*`.
- plan и fixture catalog: все provider-backed literals и файлы доказаны до
  writer, каждое требуемое свойство имеет component path/verified literal, а
  недоступная семантика provider-а отражена точным `BAQ-*`/`GAP-*`, а не
  placeholder-данными.

При `matrix-changes-required` writer один раз исправляет все findings в
`matrix-revision.md`. Если это изменяет данные, источники или связанные
сценарии, он одновременно узко обновляет plan/catalog; это не вторая revision.
Reviewer в той же отдельной сессии или новой независимой
сессии проверяет только их закрытие. Если после этой проверки осталась ровно
одна локальная неточность уже найденного finding, reviewer указывает точную
замену; writer выполняет один `micro-closure`, а reviewer проверяет только эту
замену. `Micro-closure` не может добавлять/удалять intent, требование, TC,
ветку, oracle, execution status или зависимость данных. При новом или
содержательном finding reviewer фиксирует `review-failed`. Новые автоматические
циклы запрещены.

## 5. Написание тест-кейсов

Только после `matrix-accepted` writer создаёт тест-кейсы по принятой matrix.
Один TC проверяет один основной бизнес-результат. В одном TC допустим набор
полей одного составного результата или параметризация эквивалентных данных,
если действие и реакция одинаковы.

Каждый TC содержит понятные человеку предусловия, конкретные тестовые данные
или точные свойства реально отсутствующей fixture, нумерованные шаги,
единственный основной ожидаемый результат, postconditions и трассировку к
коду/таблице/строке ФТ. Сквозная нумерация раздела должна быть непрерывной.

Выбор данных зависит от доказательства:

- сохранённый DaData fixture — для интеграционного выбора организации;
- согласованный справочник — для закрытого списка;
- сохранённый `FX-SYNTH-*` — для общих форматов и текстовых значений;
- нейтральное требование подготовки — для ролей, стендов и объектов со
  статусом, если конкретный доступ волатилен.

Не вызывай provider из шага TC и не выдавай синтетическое значение за
существующую организацию или банковский реквизит.

Если matrix требует test-data plan, writer не начинает draft TC без валидного
plan/catalog. `needs-test-data` допустим только со ссылкой на конкретный
`TDP-*`, перечнем требуемых свойств и понятной подготовкой среды; запрещены
placeholder-значения (`A`, `B`, `N/A`, «валидные данные`) вместо конкретных
literals или точного условия подготовки.

## 6. Независимое TC review и выпуск

Отдельная верхнеуровневая Codex-сессия reviewer-а читает источники, принятую
matrix и draft TC. Она формирует `test-cases-review.md` с ID сессии, verdict
`tc-accepted` или `tc-changes-required` и конкретными findings.

Reviewer проверяет трассировку, соответствие matrix, исполнимость, тестовые
данные, oracle, классы/границы, атомарность, разумную параметризацию,
смысловые дубли, no-save oracle и отсутствие выдуманных фактов. Для каждого
покрытого кода из принятой matrix он сверяет прямое присутствие кода в
трассировке TC; исключение допустимо только для кода, оставленного точным
`GAP-*`.

При замечаниях writer один раз исправляет их в `test-cases-revision.md`.
Reviewer подтверждает только закрытие findings. Применяй тот же единственный
`micro-closure`, что описан для matrix review, только для локальной неточности
уже найденного finding. При успехе изменяй статус набора на `baseline`; при
новом или оставшемся существенном замечании — `review-failed`. Не запускай ещё
один repair-loop и не скрывай draft.

Статусы отдельных TC (`needs-test-data`, `candidate-ui-calibration`,
`blocked-observability`) допустимы в baseline, если сам business result
однозначно описан ФТ. Они не являются причиной задерживать matrix или TC
review.
