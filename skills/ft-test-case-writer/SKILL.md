# FT Test Case Writer

Всегда прочитай `AGENTS.md` и `references/runtime/session-topology.md`, затем загрузи только комплект текущего этапа: для первой matrix — `references/runtime/scope-analysis.md`, `references/runtime/test-data-fixtures.md`, `references/runtime/test-design-profiles.md`, `references/runtime/test-design-matrix.md`; для материализации данных и первичных TC — `references/runtime/test-data-fixtures.md`, `references/runtime/test-case-runtime.md`; для matrix revision — `references/runtime/review-record.md`, `references/runtime/test-design-profiles.md`, `references/runtime/test-design-matrix.md`; для TC revision — `references/runtime/review-record.md`, `references/runtime/test-data-fixtures.md`, `references/runtime/test-case-runtime.md`. В той же сессии дочитывай только ещё не загруженные файлы нового этапа; не перечитывай неизменившиеся instructions и не загружай не относящиеся к этапу references. Один пакетный `Get-Content -Raw` считается полным чтением. До чтения handoff проверь, что текущая сессия зарегистрирована writer-ом выбранного scope: `runtime_session_registry.py verify --through writer --scope <scope> --expected-role writer --expected-thread-id <own-threadId>`. Matrix, TC и обе разрешённые revision выполняй только в этой writer-сессии.

До проектирования matrix сам запусти `python -X utf8 scripts/validate_runtime_scope.py <package-root> <scope-handoff-dir>` и прочитай JSON-результат. Продолжай только при `writer_allowed: true`; `blocking_errors` верни controller-у и не исправляй analyzer-owned артефакты. Все `quality_findings` используй как обязательный диагностический checklist при проектировании matrix: независимо проверь применимость каждого замечания и исправь покрытие, атомарность, формулировку или данные в matrix, если оно применимо. Неприменимый либо уже устранённый самой проекцией finding не требует нового scope-цикла. Не требуй, чтобы scope-validator вернул пустой список после создания matrix: его findings относятся к входному handoff, а закрытие проверяет независимый matrix-reviewer.

## Логический контракт данных

1. Прочитай `source-row-inventory.md`, включая `Контракт проверяемости`, `scope-brief.md`, включая `Контроль границ источника`, `Проверку согласованности` и условный `Контроль зависимых результатов`, baseline `test-data-plan.md` и карточки текущего scope из общего `work/scope-clarification-requests.md`. Артефакты analyzer-а и общий реестр вопросов доступны writer-у только для чтения.
2. Вместе с matrix создай полный writer-owned `work/practical/<scope>/matrix-data-plan.md` по `test-data-fixtures.md`: перенеси baseline без ослабления допустимых источников и добавь `TD-*`/`REL-*`, требуемые выбранными классами, границами, конфликтами и переходами. Повторные совместимые упоминания одной baseline-роли в разных группах консолидируй в одну роль полного плана с объединёнными применимыми ограничениями; конфликт источников верни controller-у как дефект baseline. До matrix review не получай внешние ответы и не подбирай произвольные конкретные сущности. Source-level дефект возвращается controller-у; недостающая роль, логически выводимая из уже принятого правила тест-дизайна, исправляется в matrix-плане writer-а.

До передачи matrix в review проверь логическую материализуемость каждого `TD-*`/`REL-*` через разрешённый механизм получения. Компоненты одной provider-bound или dictionary-bound идентичности не считай независимо управляемыми только ради таблицы решений или проверки составного ключа. Равенство одного компонента при различии другого либо иное нетривиальное ограничение между связанными записями допустимо лишь когда provider/справочник реально выдаёт такую пару, поле source-backed редактируемо после выбора либо указан отдельный утверждённый канал подготовки. Для обычного отношения «две целиком разные связные записи» достаточно воспроизводимого контракта получения двух разных записей provider-а/справочника; конкретные fixtures получают только после `matrix-accepted`. Иначе не обещай комбинацию в matrix-плане: оставь только достижимые UI-варианты и явно укажи, какая семантика требует другого уровня проверки или дополнительного источника данных. `needs-test-data` означает отсутствие конкретной стендовой привязки, а не разрешение спроектировать недостижимую комбинацию.

До `blocked-data-preparation` отличи отсутствующий вход от значения, которое создаёт сама система. Для второго примени property-check или явный runtime binding по `test-data-fixtures.md`; не требуй заранее известный системный ID и не выдумывай его. Уже в matrix назови выбранный контракт. Runtime binding используй только между независимыми точками наблюдения либо через отдельный переход; чтение и сверка одного элемента с самим собой запрещены.

Перед matrix review обязательно запусти `runtime_fixture_candidates.py`. Совместимую sibling identity добавь в matrix data plan как `сохранённый ответ`; требуемый статус/роль/доступ оставь подготовкой и `needs-test-data`, а не единственным environment-источником.

## Matrix

Создай `work/practical/<scope>/test-design-matrix.md`, `matrix-data-plan.md` и соседний `workflow-state.yaml` по `references/runtime/test-design-matrix.md`; не сохраняй matrix в `stage-handoffs`. Примени профиль к каждой строке, укажи явный элемент покрытия и отдельно укажи решение по покрытию и готовность исполнения. До подбора примеров определи применимость классов эквивалентности, границ, таблицы решений, переходов состояний, уникальности/дублей и комбинаторного покрытия; при применимости формальных техник создай одну условную `Модель покрытия` в том же файле и спроецируй все её элементы в основную таблицу. В `Источник требования` сохрани `SR-*` каждой покрываемой строки инвентаря и её первичные коды/структурные якоря ФТ. В `Тестовые данные и отношения` используй `TD-*`/`REL-*` из полного matrix-плана и точные представители только там, где сам литерал определяет класс или границу покрытия. Неразрешённые из-за недостатка источника обязанности сохрани отдельными строками: их `ID` совпадает с `GAP-*` из `coverage-gaps.md`, решение равно `coverage-gap`, готовность — `blocked-observability`. Отсутствие стендовой привязки сохраняет решение `TC` и может дать `needs-test-data`, но общий URL, логин, credentials, авторизация и доступ к модулю не являются `TD-*` и не материализуются. Запусти `python scripts/validate_runtime_matrix.py <matrix> --source-inventory <source-row-inventory.md> --coverage-gaps <coverage-gaps.md>`. Не создавай canonical TC до независимого `matrix-accepted`, SHA-256 которого совпадает с текущей matrix по `scripts/validate_runtime_review.py`.

Для профиля `границы` заполни `Контроль граничных семейств`, для `уникальность-и-дубли` — `Контроль уникальности`, а для `жизненный-цикл-создания` — явный `Контроль жизненного цикла создания` с решениями по всем трём аспектам. Validator проверяет структуру и ссылки, а reviewer — смысл; не рассчитывай на распознавание жизненного цикла по словам в формулировке. Эти таблицы не увеличивают число TC при одинаковом пути/oracle. Каждое `Не применимо` содержит конкретное source-backed основание. Для каждой попытки сохранения замкни обязательные роли и отношения данных в самой строке matrix: общие фразы о корректности остальных полей не заменяют конкретный логический контракт.

До передачи matrix в review проверь достижимость каждой точки наблюдения каждым указанным актором. Не проектируй взаимодействие с объектом, который эта роль по другой active obligation не видит. Если более сильное ограничение уже покрывает отрицательную ветку действия, явно свяжи строки `M-*` и не создавай дублирующий неисполняемый TC.

Ближайшая точка за границей и дополнительный source-backed пример по ту же сторону той же границы образуют один параметризованный класс, если у них одинаковые предусловие, control/trigger и oracle. Разные source anchors или profile tags сами по себе не обосновывают отдельные TC.

Перед matrix validator запусти `python scripts/runtime_workflow_state.py pending --matrix <matrix>`: helper привяжет writer-owned state к текущим SHA-256 matrix и `matrix-data-plan.md`. После любой matrix revision повтори `pending` и matrix validator. Не редактируй `matrix_status` вручную.

## Материализация после `matrix-accepted`

Это один явный stage, а не фоновая часть написания TC. Сначала запусти `python scripts/runtime_workflow_state.py data-start --matrix <matrix>`, затем `runtime_fixture_candidates.py` и только после этого материализуй все `TD-*`/`REL-*` принятой matrix в `work/test-data/<scope>/data-materialization.json`. `source_type` означает происхождение конкретного литерала, а не место будущей подготовки объекта: не маркируй выдуманное значение как `environment` только потому, что объект затем создадут на стенде. Совместимую sibling fixture переиспользуй с её исходным source type и зафиксируй provenance. `environment` разрешён лишь для подтверждённой привязки с hash-bound UTF-8 evidence. Не материализуй логин, URL, credentials или идентификатор обычного актора. Для provider-а сохрани связный ответ и catalog; DaData-helper используй только когда она названа в материалах пакета. Не применяй синтетику или `RUN-ID` к provider/dictionary-bound сущности. Отсутствие объекта в нужном статусе или роли доступа не блокирует materialization конкретной идентичности: TC получает литералы, подготовку и `needs-test-data`. `blocked-data-preparation` допустим только если обязательный tester-facing вход нельзя получить разрешённым источником.

Заверши stage только helper-ом: `python scripts/runtime_workflow_state.py data-complete --matrix <matrix> --materialization <data-materialization.json>`. Он сам запускает `validate_runtime_test_data.py` и фиксирует state. Для matrix без `TD-*`/`REL-*` вызови ту же команду без `--materialization`; helper установит `not-required`. Если обязательный tester-facing input нельзя получить разрешённым источником, вызови `python scripts/runtime_workflow_state.py data-blocked --matrix <matrix>` и остановись до TC. Не редактируй `data_status` вручную.

## Canonical TC

После проверки актуального `matrix-accepted` и materialization создай `test-cases/<section>-<scope>.md` по `references/runtime/test-case-runtime.md`. В `Трассировка` каждого TC укажи исполнимую `M-*` строку принятой матрицы и повтори её первичные коды либо структурные якоря ФТ. Для `needs-test-data` укажи конкретные бизнес-литералы и воспроизводимую подготовку; статус означает только отсутствие стендовой привязки. Конкретные логины, URL и credentials не фиксируй: в предусловии достаточно source-backed роли/права либо общего условия авторизации и доступа. Из полной связной fixture переноси в конкретный TC только значения, реально используемые его предусловиями, шагами или oracle. Сохрани хотя бы один конкретный materialized литерал для связанной с TC строки matrix и все значения, без которых нельзя выполнить действие либо проверить заявленное отношение; не копируй остальные поля fixture ради формальной трассировки. Проверь файл командой `python scripts/validate_runtime_tc.py <test-cases.md> --matrix <test-design-matrix.md> --data-materialization <data-materialization.json>`; для matrix без data roles аргумент materialization не нужен. Перед передачей в review вручную сверь каждое интеграционное значение в TC с materialization/fixture: точный tester-facing литерал сохраняется без сокращения, смены кавычек, регистра или иной стилистической нормализации во всех runtime-разделах TC, а не только в `Тестовые данные`. Обнови writer-owned `workflow-state.yaml`. После revision TC снова запускай validator; прежний TC review после изменения считается устаревшим.

Перед validator вручную примени обязательные gates из раздела «Правила» `references/runtime/test-case-runtime.md`: наблюдаемость перехода, восстановление состояния, допустимость очистки, конкретность идентичности/предзаполнения и выполнимость каждого шага текущим актором. Ошибка любого gate означает, что TC ещё не готов к review.

В предусловиях оформляй UI-подготовку действиями в повелительной форме; декларативно задавай только данные, роль или состояние. Для каждого успешного UI-создания проецируй отдельную проверку повторного открытия формы для второго объекта того же типа без наследования значений первого. До передачи matrix в review не оставляй в её пользовательской таблице `FX-*`/`FIX-*`: там допустимы роли `TD-*`/`REL-*`, путь сохранённого источника и нужные tester-facing литералы; внутренний fixture ID остаётся в data plan/materialization.

Перед выпуском сопоставь конкретные значения во всех runtime-разделах TC с ролями его matrix-строки. Не оставляй в предусловии, шагах или oracle materialized объект из другого сценария, даже если он использовался как шаблон при написании TC.

Для исходного статуса не пиши сокращённое действие «установить/перевести в статус». Либо задай конкретный объект и статус декларативным предусловием при `needs-test-data`, либо перечисли полный source-backed UI-переход отдельными подготовительными действиями.

Для каждого TC профиля `ролевой-доступ` явно укажи в предусловиях вход пользователем с требуемой ролью или без неё. «Подготовить пользователя» означает только наличие учётной записи и не заменяет активную сессию.

Для отрицательной проверки отсутствия не пиши действие `Найти` над самим отсутствующим элементом. Доведи актора только до достижимого родительского экрана/объекта и отдельным шагом проверь, что целевой элемент с конкретным идентификатором не отображается. Перед validator-ом сопоставь каждое действие `Найти` с oracle: один и тот же целевой объект не может одновременно быть найден и отсутствовать.

Не доказывай повторяемость одной фразой «одноразовый изолированный объект». Сверь identity tuple всех TC набора: одноразовые объекты разных TC должны различаться конкретными ключами. Если используется один и тот же объект, укажи source-backed восстановление либо подтверждённый setup/reset-контракт среды; статус `needs-test-data` сам по себе изоляцию не создаёт.

Если cleanup выполняет другая роль, распиши в постусловиях отдельные действия входа, повторной навигации, поиска конкретного объекта и source-backed восстановления. Не сворачивай смену актора и действие в одну фразу. Для отрицательного ролевого oracle повтори точное различие источника между «не отображается» и «отображается, но недоступно».

Не используй делегирующие шаги «Выполнить добавление/создание/редактирование/сценарий»: текущий TC должен содержать наблюдаемые действия и значения, достаточные для ручного выполнения и автоматизации. В проверках счётчиков можно использовать измеренный baseline `N` и дельту, но только при явной фиксации значения до действия, полном описании вызывающей операции и повторном измерении того же показателя.

Не уплотняй полный UI-путь в один нумерованный пункт. Один пункт раздела `Шаги` или исполнимых `Постусловий` содержит одно пользовательское действие либо одну проверку; последовательность «открыть → найти → нажать → найти → навести → нажать» оформляется отдельными пунктами. Это правило не меняет атомарность TC: один кейс по-прежнему может иметь много шагов, если у него одна проверяемая цель и один основной oracle.

Проецируй условие доступности контрола в каждый TC, где он используется. Если matrix/source требует hover, раскрытия блока или открытия меню, повтори этот UI-триггер непосредственно перед нажатием — в шагах, предусловиях и постусловиях. Не полагайся на отдельный TC, который проверяет видимость того же контрола.

Не пиши «найти партнёра/объект/запись в статусе ...» без конкретного признака из тестовых данных. Переноси materialized identity tuple в подготовку, поиск, шаги и cleanup. Для дочернего объекта добавляй родительский контекст, если источник не подтверждает глобальную уникальность ключа ребёнка.

Разделяй полную идентичность подготовленного объекта и UI-признаки его выбора. В декларативном предусловии укажи полный identity tuple, а в команде поиска — только source-backed поля, видимые в этой точке интерфейса. Не добавляй скрытый ключ в действие поиска ради формальной конкретности.

Для вложенной сущности после входа или смены актора распиши полный путь: исходный экран → поиск родителя по видимому признаку → переход в родителя → поиск ребёнка. Не заменяй его фразой «открыть список дочерних объектов родителя».

В oracle видимости, отсутствия или открытия объекта укажи видимый литерал из тестовых данных либо явно свяжи результат с ранее точно найденным объектом. Не оставляй обезличенное «блок отображается».

Для предзаполненной формы редактирования перечисли в oracle конкретные поля и их ожидаемые литералы. Фраза «с заданными значениями» не является проверкой.

Если проверка опирается на применимое временное решение БА, сохрани текущий ожидаемый результат и добавь поле `Требуется актуализация` с условием пересмотра из analyzer-owned раздела `Временные решения`. Это не меняет `Статус исполнения` и не блокирует выпуск текущего TC.

Не создавай internal IDs, gaps, fixtures или просьбы о данных в production TC. Не выполняй больше одной revision без нового решения пользователя и не создавай для revision новую writer-сессию. При revision изменяй только элементы из `affected_items` конечных findings. Если исправление действительно требует соседнего элемента, измени его явно: manifest безопасно повысит re-review до полного; не скрывай дополнительный diff ради сохранения delta.

При revision сначала прочитай переданный review-record и проверь его штатным validator-ом. Если TC review возвращает `repair_stage: matrix`, не исправляй canonical TC напрямую: сначала исправь matrix, передай её на независимый matrix re-review и только после нового `matrix-accepted` заново спроецируй затронутые TC. На этапе повторной проекции снова прочитай исходный TC review-record, примени все findings с `origin_stage: tc|both` и изменения принятой matrix; no-op с неизменным SHA canonical TC не закрывает такие findings. При `repair_stage: tc` не меняй принятую matrix и исправляй только canonical TC. Перед возвратом controller повторно прочитай каждый TC из `affected_items` каждого finding и выполни residual-check по формулировке требуемой коррекции; в финале writer перечисли `finding_id`, проверенные TC и `остаточных нарушений: 0`. Частичное массовое исправление без проверки каждого затронутого TC не считается завершённой revision.
