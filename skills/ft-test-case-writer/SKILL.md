# FT Test Case Writer

Используй этот skill только для изолированной writer-фазы. Для нового полного
scope по умолчанию используй [ft-practical-route](../ft-practical-route/SKILL.md):
он сначала принимает matrix независимым reviewer-ом.

Перед работой прочитай [practical route v1](../../references/agent/practical-test-case-route-v1.md),
[runtime format TC](../../references/qa/test-case-runtime-format.md) и
[coverage checklist](../../references/qa/coverage-runtime-checklist.md).

## Входы

- выбранный scope, его DOCX/XHTML/PDF/support/visual inputs и `AGENT-NOTES.md`;
- `source-scope.md`, применимые ответы БА и принятая matrix;
- findings reviewer-а, если пользователь запросил одну разрешённую revision.

## Выходы

- текущая matrix либо набор TC текущего scope;
- при revision — краткий файл с закрытием каждого finding.

## Правила

1. Один TC имеет один основной business result. Объединяй только поля одного
   составного результата либо эквивалентные значения с одним действием и одной
   реакцией.
2. Сохраняй коды требований, таблицы/строки и source refs. Не выдумывай
   бизнес-правило по макету или названию поля.
3. Runtime-поля TC пиши по-русски. Не включай URL, логины, пароли, токены,
   конкретные учётные записи или внутренние setup-идентификаторы.
4. Тестовые данные содержат конкретные сохранённые значения/файлы либо точные
   свойства отсутствующей fixture. Интеграционный fixture, синтетические
   данные и закрытые справочники не взаимозаменяемы.
5. Для успешного create укажи бизнес-ключ, исходное отсутствие и очистку; для
   отмены/закрытия — отсутствие сохранения или изменения.
6. Для source-defined формата и границ перечисли применимые классы, а не один
   случайный невалидный пример. Не склеивай valid и rejection checks.
7. Перед matrix review проверь, что применимые глобальные правила типов данных
   внесены в scope и matrix; корректные значения не нарушают другой constraint,
   а невалидные классы следуют из источника. Перед TC review проверь покрытие
   matrix, непрерывность нумерации, трассировку, дубли, primary oracle и
   соответствие тестовых данных действиям. Для каждого save/cancel проверь
   полноту зависимых обязательных данных и oracle отсутствия сохранения; для
   параметризации зафиксируй одно действие, одну реакцию и краткое обоснование.

## Ограничения

- Не запускай reviewer в той же сессии и не изменяй его findings.
- Не создавай manifests, receipts, workflow state или repair-loop.
- Не превращай gap или source contradiction в выдуманный executable TC.
