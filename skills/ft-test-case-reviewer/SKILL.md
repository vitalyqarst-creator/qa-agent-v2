# FT Test Case Reviewer

До review прочитай `AGENTS.md`, `references/runtime/session-topology.md`, `references/runtime/scope-analysis.md`, `references/runtime/test-data-fixtures.md`, `references/runtime/test-design-profiles.md`, `references/runtime/test-design-matrix.md`, `references/runtime/test-case-runtime.md` и `references/runtime/review-record.md`.

Review выполняется только в отдельной верхнеуровневой Codex-сессии. Итог сохрани в `work/reviews/<scope>/<matrix|tc>-review.md`: ссылка/идентификатор сессии, режим, verdict и конечный список findings. Рядом создай `<matrix|tc>-review.json`, связанный с SHA-256 проверенного artifact. Для каждого finding перечисли точные `affected_items`; `GLOBAL` используй только для глобального дефекта. Перед validator запусти `runtime_review_delta.py enrich-review`, затем `scripts/validate_runtime_review.py`. Не создавай attestation, immutable snapshot, dispatch receipt или технический transcript.

Начинай review только после operational prompt controller-а с путём dispatch receipt. Первым действием проверь receipt командой `scripts/runtime_review_dispatch.py verify` из `review-record.md`: она также подтверждает роль текущей сессии в package registry, совпадение `runtime_commit`, режим и revision manifest. Если receipt отсутствует, stale, относится к другому artifact/prompt/thread, не требует `codex-thread` или сессия зарегистрирована для прежнего commit agent-layer, остановись без чтения review inputs и без verdict. Reviewer не создаёт и не заменяет dispatch receipt. Повторное review после разрешённой правки выполняй в этой же reviewer-сессии только при неизменном runtime commit; после обновления agent-layer controller обязан создать новую верхнеуровневую reviewer-сессию. Не переходи между matrix и TC review.

При `review_mode: full` выполни полный проход ниже. При `review_mode: delta` сначала полностью запусти штатный artifact validator, затем прочитай прежние findings из manifest, только перечисленные `changed_items`, связанные строки matrix/inventory и точные source fragments. По hashes считай остальные элементы неизменными и не загружай заново все primary/visual inputs. Всё равно проверь глобальные машинные gates: проекцию, уникальность, нумерацию и дубли. Если обнаружена зависимость за пределами manifest, повысь текущий review до `full`, проверь весь artifact и перечисли все его элементы в `reviewed_items`; не запускай второй reviewer и не выдавай частичный verdict.

Первый `full` review охватывает все элементы проверяемого artifact, но не весь FT-пакет. Полностью прочитай выбранный раздел scope в каноническом и нормализованном источниках, затем точные таблицы, строки, рисунки, коды и support/visual anchors, зарегистрированные для этого scope в inventory и brief. PDF/рендер открывай только при `visual_crosscheck: required` и только на относящихся к scope страницах и рисунках. Не перечитывай другие разделы ФТ только для общей подстраховки. Расширяй source slice лишь когда выбранный раздел или зарегистрированный anchor явно ссылается на внешний фрагмент либо когда для проверки найденного противоречия нужен соседний источник; перечисли такие расширения и причины в Markdown review. Теги и ссылки writer-а не заменяют независимую проверку полноты всего выбранного раздела.

## Matrix review

До содержательного review заново запусти matrix-validator с `--source-inventory` и `--coverage-gaps`; неполная проекция блокирует review.

В режиме `full` сверь matrix заново с полным source slice выбранного scope по правилу выше, `source-row-inventory.md`, включая `Контракт проверяемости`, `scope-brief.md`, включая `Проверку согласованности`, карточками текущего scope в `work/scope-clarification-requests.md`, `test-data-plan.md` и доступным `fixture-catalog.json`. Отдельно оцени решение по покрытию и готовность исполнения. В режиме `delta` применяй ограничение из общего правила выше.

До оценки строк matrix проверь входной inventory: один `SR-*` должен соответствовать одной обязанности, все утверждения из таблиц должны содержать ссылку на таблицу и точный текст существующей строки первого столбца нормализованного машинного источника, а отменённые утверждённым ответом требования должны находиться в разделе применённых исключений и отсутствовать среди активных `SR-*`. Независимые свойства разных ячеек одной строки — обязательность, редактируемость, представление, ссылка/переход и состав данных — должны быть разнесены по отдельным `SR-*`; одна строка таблицы может повторяться. Соседний абзац и элемент примечания не должны быть выданы за строку таблицы. Если строка таблицы и связанный код требования называют разные объекты, действия или результаты, требуй отдельный пробел по противоречию; молчаливая нормализация под контекст запрещена. Убедись, что visual cross-check охватывает каждый включённый UI-уровень и каждый локальный путь дословно совпадает с зарегистрированным source locator-ом существующим файлом.

Независимо восстанови элементы покрытия из источников, а не из тегов writer-а. Для ограничений проверь полноту непересекающихся допустимых/недопустимых классов и вычислимых граничных точек; для зависимости результата от двух и более условий — допустимые правила таблицы решений; для статусов — все source-backed переходы; для трёх и более взаимодействующих факторов — обоснованность комбинаторного профиля, ограничений и выбранной силы покрытия. Если формальная техника применима, каждый `EP-*`, `BVA-*`, `DT-R*`, `ST-T*` или `CT-C*` должен существовать в единой модели и проецироваться ровно в одну строку matrix. Не требуй формальную модель там, где техника неприменима.

Проверь не только наличие, но и смысл `Контракта проверяемости`: каждая активная `SR-*` должна иметь один конкретный объект/UI-уровень, применимое условие, событие и наблюдаемый результат. Не принимай формальные перефразы исходной обязанности. В `Проверке согласованности` оцени все семь аспектов; `Не применимо` допустимо только с конкретной причиной, а применимый вывод должен быть связан с `SR-*` или `GAP-*`.

Каждый `GAP-*` должен ссылаться ровно на одну атомарную `SR-*`, иметь допустимый source-level класс и переносить эту же связь в отдельную строку matrix с решением `coverage-gap` и готовностью `blocked-observability`. Общий вопрос БА может закрывать несколько GAP, но разные объекты, UI-уровни и обязанности не объединяются в один пробел покрытия. Отсутствие стендовой записи, учётной записи, URL, credentials или доступа к среде не является GAP.

Ответ `working-assumption` с непросроченным текущим поведением и `blocking: no` должен быть применён, а не оставлен GAP. Проверь, что условие его будущей актуализации сохранено в scope brief и затем в соответствующем TC. Не требуй окончательной будущей модели для проверки явно разрешённого текущего поведения.

Блокируй matrix, если:

- пропущена обязанность или context dimension;
- потерян код требования или строка источника; ссылка только на таблицу не заменяет существующий буквенно-цифровой код;
- `coverage-gap` создан только из-за отсутствия готовой записи, учётной записи, URL, credentials или доступа к стенду;
- как `ready` запланирована проверка без конкретных данных/подготовки либо как TC запланирована обязанность без наблюдаемого business oracle;
- данные не соответствуют механизму получения: произвольный текст использован вместо значения внешнего сервиса/справочника либо связанные реквизиты собраны из разных записей;
- один клик/выбор разбит на однотипные TC без отдельной бизнес-логики;
- разные невалидные классы с разным риском ошибочно слиты;
- пропущен применимый универсальный профиль, обязательное поле или source-backed роль;
- отсутствует элемент покрытия, применимая формальная модель неполна, либо пример выбран до определения класса, границы, правила, перехода или комбинации;
- таблица решений не покрывает допустимое сочетание условий, переходная модель теряет source-backed переход либо pairwise объявлен достаточным без основания;
- дублирующие строки имеют одну сигнатуру и отличаются только эквивалентным параметром;
- строка требует от актора взаимодействовать с объектом или элементом, который недостижим ему в этом состоянии по другой active obligation;
- отрицательная ветка ошибочно объявлена непокрытой без проверки явного source-backed логического покрытия другой строкой matrix, например невидимости самого объекта для этой роли;
- ролевой oracle в matrix ослабляет точную семантику источника: «видим и доступен только» требует отсутствия элемента у другой роли, а не общего «действие недоступно»;
- в user-facing matrix остался английский process text.

Вердикт: только `matrix-accepted` или `matrix-changes-required` с конечным списком findings.

## TC review

До содержательного review заново запусти TC-validator с `--matrix`; неполная проекция принятой матрицы блокирует review.

В режиме `full` проверь весь canonical TC artifact по принятой matrix, полному source slice выбранного scope и fixture catalog; в режиме `delta` примени те же критерии к изменённым TC и их зависимостям. Обязательно блокируй:

- process IDs и `GAP-*` вне `Трассировка`;
- неконкретные тестовые данные;
- описание источника вместо значения («фиксированный запрос», «организация из снимка», «ожидаемые реквизиты»);
- интеграционное значение, не совпадающее с сохранённой fixture;
- отсутствует поле `Требуется актуализация` для TC, основанного на применимом временном решении БА;
- требование получить fixture в TC;
- действие тестировщика, дублирующееся между предусловиями и шагами;
- подготовительное действие, которое выдаёт промежуточный результат за факт;
- `needs-test-data` без конкретных литералов и воспроизводимой подготовки либо `blocked-observability` в финальном runtime TC;
- `candidate-ui-calibration`, который не соответствует узкой политике из `test-design-profiles.md`;
- неисполняемый expected result или лишнее объединение независимых проверок.
- переход, изменение значения или счётчика, которое уже выполнено в предусловиях и поэтому не наблюдается в шагах;
- изменяющий состояние TC без source-backed восстановления или явного одноразового изолированного объекта;
- выдуманный cleanup: удаление, сброс, прямое изменение БД или иной способ, которого нет в источнике либо контракте среды;
- переход/предзаполнение без проверки конкретной идентичности объекта или ожидаемых литералов полей;
- шаг над объектом, который недоступен или невидим текущему актору в зафиксированном состоянии.
- гибридное предусловие «установить/перевести объект в статус» без полного source-backed перехода: требуй либо декларативное исходное состояние конкретного объекта, либо отдельные исполнимые подготовительные действия;
- TC профиля `ролевой-доступ`, в котором учётная запись только подготовлена, но отсутствует явный вход пользователем требуемой роли перед целевыми шагами;
- отрицательный ролевой oracle «недоступно», если источник требует невидимость элемента, либо невидимость, если источник требует disabled-состояние;
- постусловие, которое сворачивает смену актора и действие в одну фразу или после нового входа не повторяет навигацию и поиск конкретного объекта;
- делегирующий шаг «Выполнить добавление/создание/редактирование/сценарий» вместо явных действий и значений текущего TC;
- нажатие условно доступного контрола без обязательного UI-триггера из matrix/source непосредственно перед ним, включая предусловия и постусловия;
- поиск или декларативная подготовка произвольной записи по статусу/типу вместо identity tuple из тестовых данных; для дочернего объекта проверь также родительский контекст, если его ключ не доказан как глобально уникальный;
- UI-поиск по полю, которое не отображается в данной точке по source/matrix. Полный identity tuple должен доказывать подготовку объекта, но исполнимая команда поиска использует только видимые устойчивые признаки;
- неполный путь к вложенной сущности после входа или смены актора: должны быть исходный экран, поиск видимого родителя, переход в него и поиск ребёнка, если иной прямой маршрут не подтверждён source;
- обезличенный oracle видимости/отсутствия/открытия, который не содержит видимого литерала и не ссылается однозначно на ранее найденный объект;
- oracle предзаполнения формы редактирования без конкретных пар поле–ожидаемый литерал;

Не требуй отдельный отрицательный TC на отсутствие действия внутри объекта, если принятая matrix явно связывает это ограничение с более сильным source-backed результатом — объект целиком не виден тому же актору. Такой TC был бы неисполняемым; проверяй связанное покрытие, а не механическое число TC на каждую формулировку.

Не отклоняй измеряемый baseline `N` только потому, что это не литерал. Для проверки счётчика он допустим, если значение фиксируется до действия, действие описано полностью, а ожидаемый результат задаёт проверяемую дельту для того же показателя. Отклоняй непрозрачное действие или незафиксированный baseline, а не саму переменную.

Также проверь повторяющиеся ключи данных, корректность параметризации, сквозную нумерацию, группировку по функциональности и дубли по сигнатуре проверки. Вердикт: только `tc-accepted` или `tc-changes-required`. Принимать набор с material waiver нельзя.

Для каждого finding при `tc-changes-required` укажи `origin_stage` по `references/runtime/review-record.md`. Сравни дефект не только с ФТ, но и с принятой matrix: `matrix` допустим только когда проверенный TC уже корректен и после исправления matrix не требует изменения; `tc` — когда matrix достаточна, но writer неверно спроецировал её в TC; `both` — когда исправить нужно оба артефакта, включая случай, когда пропуск matrix уже привёл к пропуску покрытия в TC. Не помечай дефект как `matrix` только потому, что его первопричина находится выше по маршруту.

Первый TC review и manifest-driven `full` fallback являются полным проходом ограниченного artifact, а не fail-fast проверкой. Даже после первого material finding проверь каждый TC по всем обязательным gates, затем сгруппируй одинаковые дефекты и перечисли все затронутые TC. Перед verdict зафиксируй число проверенных TC. При `delta` проверь каждый изменённый TC и закрытие каждого прежнего finding; неизменные TC не перечитывай без зависимости. Не запускай второй проход только ради поиска замечаний, которые должны были войти в текущий объём.

В schema v2 review JSON запиши `artifact_index`, `semantic_input_hashes`, `reviewed_items` и `review_scope_complete: true` через штатный helper. Для полного TC review оба счётчика равны общему числу и в Markdown укажи `Проверено TC: N/N`; для delta `reviewed_tc_count` равен числу изменённых TC и укажи `Проверено изменённых TC: K/N`. Без этих полей итог невалиден и не передаётся controller-у.
