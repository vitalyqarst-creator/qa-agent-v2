# FT Test Case Reviewer

До review прочитай `AGENTS.md`, `references/runtime/session-topology.md`, `references/runtime/scope-analysis.md`, `references/runtime/test-data-fixtures.md`, `references/runtime/test-design-profiles.md`, `references/runtime/test-design-matrix.md`, `references/runtime/test-case-runtime.md` и `references/runtime/review-record.md`. Загрузи этот обязательный комплект ровно один раз за сессию: один пакетный `Get-Content -Raw` считается полным чтением каждого файла. Не перечисляй размеры файлов перед чтением и не перечитывай их по одному, если вывод не был усечён и файл не изменился.

Review выполняется только в отдельной верхнеуровневой Codex-сессии. Итог сохрани в `work/reviews/<scope>/<matrix|tc>-review.md`: ссылка/идентификатор сессии, режим, verdict и конечный список findings. Рядом создай `<matrix|tc>-review.json`, связанный с SHA-256 проверенного artifact. Для каждого finding перечисли точные `affected_items`; `GLOBAL` используй только для глобального дефекта. Перед validator запусти `runtime_review_delta.py enrich-review`, затем `scripts/validate_runtime_review.py`. Не создавай attestation, immutable snapshot, dispatch receipt или технический transcript.

Начинай review только после operational prompt controller-а с путём dispatch receipt. Первым действием проверь receipt командой `scripts/runtime_review_dispatch.py verify` из `review-record.md`: она также подтверждает роль текущей сессии в package registry, совпадение `runtime_commit`, режим и revision manifest. Если receipt отсутствует, stale, относится к другому artifact/prompt/thread, не требует `codex-thread` или сессия зарегистрирована для прежнего commit agent-layer, остановись без чтения review inputs и без verdict. Reviewer не создаёт и не заменяет dispatch receipt. Повторное review после разрешённой правки выполняй в этой же reviewer-сессии только при неизменном runtime commit; после обновления agent-layer controller обязан создать новую верхнеуровневую reviewer-сессию. Не переходи между matrix и TC review.

При `review_mode: full` выполни полный проход ниже. При `review_mode: delta` сначала полностью запусти штатный artifact validator, затем прочитай прежние findings из manifest, только перечисленные `changed_items`, связанные строки matrix/inventory и точные source fragments. Для matrix delta также полностью прочитай изменённый writer-owned `matrix-data-plan.md`, если он перечислен в `changed_semantic_inputs`: это обязательная companion-проекция, но не основание перечитывать весь source slice. По hashes считай остальные элементы неизменными и не загружай заново все primary/visual inputs. Всё равно проверь глобальные машинные gates: проекцию, уникальность, нумерацию и дубли. Если обнаружена зависимость за пределами manifest, повысь текущий review до `full`, проверь весь artifact и перечисли все его элементы в `reviewed_items`; не запускай второй reviewer и не выдавай частичный verdict.

Первый `full` review охватывает все элементы проверяемого artifact, но не весь FT-пакет. Полностью прочитай выбранный раздел scope в каноническом и нормализованном источниках, затем точные таблицы, строки, рисунки, коды и support/visual anchors, зарегистрированные для этого scope в inventory и brief. PDF/рендер открывай только при `visual_crosscheck: required`, только на относящихся к scope страницах и рисунках и только через `scripts/render_runtime_pdf.py`; не запускай Poppler/LibreOffice напрямую и не создавай `tmp/` внутри репозитория. Не перечитывай другие разделы ФТ только для общей подстраховки. Расширяй source slice лишь когда выбранный раздел или зарегистрированный anchor явно ссылается на внешний фрагмент либо когда для проверки найденного противоречия нужен соседний источник; перечисли такие расширения и причины в Markdown review. Теги и ссылки writer-а не заменяют независимую проверку полноты всего выбранного раздела.

## Matrix review

Вместе с matrix проверяй writer-owned `work/practical/<scope>/matrix-data-plan.md`. Он должен переносить analyzer baseline без ослабления источников и замыкать все `TD-*`/`REL-*` matrix. Дополнительная роль, логически возникшая из применённого профиля, не является дефектом analyzer baseline, если полный matrix-план задаёт её источник и отношения.

До содержательного review заново запусти `python -X utf8 scripts/validate_runtime_scope.py <package-root> <scope-handoff-dir>` для analyzer-owned handoff и matrix-validator с `--source-inventory` и `--coverage-gaps`. Продолжай только при `writer_allowed: true`; неполная проекция блокирует review. Используй все `quality_findings` scope-validator-а как независимый диагностический checklist: проверь, что применимые замечания действительно устранены в matrix, а не просто проигнорированы writer-ом. Неприменимый finding не является автоматическим дефектом matrix и не требует изменения analyzer-owned артефактов.

Первый `full` matrix review не является fail-fast. До формулирования verdict заполни в review JSON `matrix_review_checklist` по всем категориям из `review-record.md`: покрытие источника, формальные техники, жизненный цикл уникальности, замыкание данных сохранения, происхождение идентичности, материализуемость данных, достижимость/oracles и дубли/параметризация. В `identity-provenance` перечисли каждую целевую и prerequisite/родительскую сущность и восстановленный источник её tester-facing идентичности; будущая стендовая подготовка не является таким источником. В `data-materializability` перечисли provider/dictionary-bound отношения и проверь их логическую достижимость. Для нетривиального равенства/различия компонентов одной связной идентичности требуется фактическая возможность provider-а/справочника, source-backed редактирование либо утверждённый канал подготовки. Для двух целиком разных связных записей достаточно воспроизводимого контракта получения разных записей; не требуй конкретные fixtures до `matrix-accepted`. `needs-test-data` и будущая стендовая подготовка сами по себе не доказывают достижимость нетривиальной комбинации. Сначала независимо восстанови ожидаемые элементы каждой применимой категории, затем проверь все строки matrix, и только после этого консолидируй конечный список findings. `not-applicable` требует конкретного source-backed основания. Не выпускай промежуточный record после нахождения первых дефектов.

В режиме `full` сверь matrix заново с полным source slice выбранного scope по правилу выше, `source-row-inventory.md`, включая `Контракт проверяемости`, `scope-brief.md`, включая `Контроль границ источника`, распределение родительских обязанностей, контроль полноты строк таблиц, реестр обработки визуальных входов и `Проверку согласованности`, карточками текущего scope в `work/scope-clarification-requests.md` и `test-data-plan.md`. До принятия matrix не требуй уже материализованный fixture catalog. Проверь вводный и завершающий текст родительского раздела: каждое нормативное утверждение должно быть атомарно назначено правильному объекту и scope; механическое включение всего родительского фрагмента в текущий scope является дефектом так же, как его потеря. Для каждой используемой таблицы независимо сравни полный перечень строк первого столбца XHTML с таблицей контроля и inventory. Убедись, что каждый зарегистрированный visual/Figma input имеет явное решение; если локальный макет оставляет неизвестным релевантный UI-элемент, подпись, точку наблюдения или путь, статус «локальных материалов достаточно» является дефектом — должна быть зафиксирована одна попытка Figma либо её недоступность. Для количественного ограничения проверь шаг представления, точную допустимую границу, ближайшее представимое недопустимое значение и источник самого предела либо честный GAP. Тип поля и платформенный default не являются основанием min/max. Отдельно оцени решение по покрытию и готовность исполнения. В режиме `delta` применяй ограничение из общего правила выше.

До оценки строк matrix проверь входной inventory: один `SR-*` должен соответствовать одной обязанности, все утверждения из таблиц должны содержать ссылку на таблицу и точный текст существующей строки первого столбца нормализованного машинного источника, а отменённые утверждённым ответом требования должны находиться в разделе применённых исключений и отсутствовать среди активных `SR-*`. Определение термина, пояснение бизнес-смысла или структурный контекст без самостоятельного наблюдаемого результата не являются активным `SR-*`; отклоняй также дубли, где этот контекст повторяет явное требование к полю, справочнику или действию. Сохрани любой проектный код требования при наличии; для требования без кода требуй точную строку таблицы либо раздел вместе с короткой точной цитатой абзаца/элемента списка. Независимые результаты и свойства — открытие поверхности, предзаполнение, обязательность, редактируемость, представление, ссылка/переход и состав данных — должны быть разнесены по отдельным `SR-*`; одна строка или код источника может повторяться. Один `SR-*` и одна строка контракта называют ровно один объект или UI-уровень: партнёр и реквизит, список и карточка либо иные независимо наблюдаемые поверхности разделяются. Для обязательности не принимай выдуманную disabled-кнопку, подсветку или сообщение: без отдельного источника допустим лишь нейтральный результат, что объект с пустым полем не сохраняется. Соседний абзац и элемент примечания не должны быть выданы за строку таблицы. Если строка таблицы и связанный код требования называют разные объекты, действия или результаты, требуй отдельный пробел по противоречию; молчаливая нормализация под контекст запрещена. Убедись, что visual cross-check охватывает каждый включённый UI-уровень и каждый локальный путь дословно совпадает с зарегистрированным source locator-ом существующим файлом.

Независимо восстанови элементы покрытия из источников, а не из тегов writer-а. Для ограничений проверь полноту непересекающихся допустимых/недопустимых классов и вычислимых граничных точек; для зависимости результата от двух и более условий — допустимые правила таблицы решений; для статусов — все source-backed переходы; для трёх и более взаимодействующих факторов — обоснованность комбинаторного профиля, ограничений и выбранной силы покрытия. Если формальная техника применима, каждый `EP-*`, `BVA-*`, `DT-R*`, `ST-T*` или `CT-C*` должен существовать в единой модели и проецироваться ровно в одну строку matrix. Не требуй формальную модель там, где техника неприменима.

Для source-backed уникальности независимо восстанови бизнес-ключ и область уникальности. Проверь точный дубль, межтиповой/межкатегорийный вариант при глобальном правиле, одинаковый ключ у другого родителя при локальном правиле, самосовпадение при редактировании и конфликт с другим объектом, если создание и редактирование поддерживаются. Когда ключ не включает все поля, потребуй вариант с тем же ключом и изменённым неключевым полем. Нормализацию регистра, пробелов и пунктуации не требуй без источника.

Отдельно восстанови логический контракт данных. Каждая целевая и prerequisite/родительская сущность должна иметь `TD-*`, source-compatible механизм и нужные отношения; источник идентичности наследуется между scope. Provider/dictionary-bound роль нельзя заменить синтетикой или `RUN-ID`. Если один control принимает несколько альтернативных ключей поиска/ввода, проверь покрытие каждого ключа; одинаковые path/oracle должны быть параметризованы, а не размножены.

Проверь достижимость отношений внутри связной provider/dictionary-bound идентичности. Не принимай план, который требует одинаковый provider-bound идентификатор при другом provider-bound наименовании, либо иную независимую вариацию связанных полей, если не приведён один из трёх контрактов: фактически доступная пара записей provider-а/справочника, source-backed редактирование конкретного поля после выбора или утверждённый отдельный канал подготовки. Обычное получение двух целиком разных связных записей не относится к такой независимой вариации: до принятия matrix для него достаточно явного воспроизводимого acquisition-контракта, а фактические fixtures проверяются на materialization-этапе. Механическая полнота таблицы решений не оправдывает недостижимый UI-сценарий.

Проверь не только наличие, но и смысл `Контракта проверяемости`: каждая активная `SR-*` должна иметь один конкретный объект/UI-уровень, применимое условие, событие и наблюдаемый результат. Не принимай формальные перефразы исходной обязанности. В `Проверке согласованности` оцени все семь аспектов; `Не применимо` допустимо только с конкретной причиной, а применимый вывод должен быть связан с `SR-*` или `GAP-*`.

Каждый `GAP-*` должен ссылаться ровно на одну атомарную `SR-*`, иметь допустимый source-level класс и переносить эту же связь в отдельную строку matrix с решением `coverage-gap` и готовностью `blocked-observability`. Примени gate частичной тестируемости: если исходное утверждение содержит хотя бы один детерминированный результат, потребуй отдельные `SR-*`/`TC` для таких результатов и разреши GAP только для неизвестного атома или исчерпывающей полноты. Прямо связанный рисунок/макет можно использовать для конкретизации наблюдаемых элементов уже заданного текстом результата, но не для создания бизнес-правила. Общий вопрос БА может закрывать несколько GAP, но разные объекты, UI-уровни и обязанности не объединяются в один пробел покрытия. Отсутствие стендовой записи, учётной записи, URL, credentials или доступа к среде не является GAP.

Ответ `working-assumption` с непросроченным текущим поведением и `blocking: no` должен быть применён, а не оставлен GAP. Проверь, что условие его будущей актуализации сохранено в scope brief и затем в соответствующем TC. Не требуй окончательной будущей модели для проверки явно разрешённого текущего поведения.

Причинная связь `SR-*` может пересекать source anchors. Проверь `Контроль зависимых результатов`: GAP причины даёт зависимому oracle свой GAP либо точное source-backed основание независимости. Не принимай готовый индикатор/представление при противоречивом причинном переходе.

Блокируй matrix, если:

- пропущена обязанность или context dimension;
- проверяемая часть составного требования поглощена `coverage-gap` из-за неизвестности другой части;
- потерян существующий код требования с любым проектным обозначением либо точный структурный якорь требования без кода; ссылка только на раздел или таблицу недостаточна;
- `coverage-gap` создан только из-за отсутствия готовой записи, учётной записи, URL, credentials или доступа к стенду;
- как `ready` запланирована проверка без логического контракта данных/подготовки либо как TC запланирована обязанность без наблюдаемого business oracle;
- роли данных не соответствуют механизму получения, prerequisite-сущность потеряла свой provider/dictionary source, либо provider-bound identity изменяется через `RUN-ID`;
- пропущен один из альтернативных source-backed ключей поиска/ввода или одинаковый path/oracle ошибочно размножен вместо параметризации;
- системно создаваемый output выдан за заранее известный вход вместо property-check или runtime binding из `test-data-fixtures.md`;
- строка с системно создаваемым output не выбирает проверку свойства либо не называет раздельные точки фиксации и сверки runtime binding;
- один клик/выбор разбит на однотипные TC без отдельной бизнес-логики;
- обязательные read-only outputs одного source-backed выбора разнесены по недостижимым пустым состояниям вместо одной строки `зависимая-обязательность` с общим отказом сохранения;
- разные невалидные классы с разным риском ошибочно слиты;
- пропущен применимый универсальный профиль, обязательное поле или source-backed роль;
- профиль `уникальность-и-дубли` не определяет source-backed бизнес-ключ, область уникальности или применимые create/edit варианты;
- отсутствует элемент покрытия, применимая формальная модель неполна, либо пример выбран до определения класса, границы, правила, перехода или комбинации;
- таблица решений не покрывает допустимое сочетание условий, переходная модель теряет source-backed переход либо pairwise объявлен достаточным без основания;
- дублирующие строки имеют одну сигнатуру и отличаются только эквивалентным параметром;
- строка требует от актора взаимодействовать с объектом или элементом, который недостижим ему в этом состоянии по другой active obligation;
- отрицательная ветка ошибочно объявлена непокрытой без проверки явного source-backed логического покрытия другой строкой matrix, например невидимости самого объекта для этой роли;
- ролевой oracle в matrix ослабляет точную семантику источника: «видим и доступен только» требует отсутствия элемента у другой роли, а не общего «действие недоступно»;
- в user-facing matrix остался английский process text.

Вердикт: только `matrix-accepted` или `matrix-changes-required` с конечным списком findings.

Только при manifest-backed re-review после writer revision классифицируй каждый текущий finding через `discovery_status` из `review-record.md`. Новый дефект неизменённого элемента, который должен был быть найден предыдущим валидным полным review, помечай `prior-review-omission`, а весь record — `review_quality_status: failed-prior-review-incomplete`; не выдавай его за дефект, созданный revision. Fresh full review, заменяющий record, который стал невалиден после изменения runtime-контракта, не сравнивай с невалидным predecessor: верни обычный полный verdict со всеми текущими findings. Дефект, реально возникший в изменённом элементе, допускает `introduced-by-revision`; дефект из изменившегося semantic input — `semantic-input-change`; прежний незакрытый finding — `carried-forward` со ссылкой на прежний ID. Controller маршрутизирует качество только по `review_quality_blocking` validator-а.

## TC review

До содержательного review сначала определи, использует ли принятая matrix `TD-*`/`REL-*`. Если использует — заново запусти materialization-validator, затем TC-validator с `--matrix` и `--data-materialization`; неполная проекция или неподтверждённые данные блокируют review. Если не использует — materialization-validator не запускай, проверь в writer `workflow-state.yaml` значение `data_status: not-required`, отсутствие фиктивного `data-materialization.json` и запусти TC-validator только с `--matrix`. Отсутствие materialization в этой ветке не является blocker-ом.

В режиме `full` проверь весь canonical TC artifact по принятой matrix, полному source slice выбранного scope, `data-materialization.json` и fixture catalog; в режиме `delta` примени те же критерии к изменённым TC и их зависимостям. Обязательно блокируй:

- process IDs и `GAP-*` вне `Трассировка`;
- неконкретные тестовые данные;
- описание источника вместо значения («фиксированный запрос», «организация из снимка», «ожидаемые реквизиты»);
- интеграционное значение, не совпадающее с сохранённой fixture;
- поля связной fixture, которые не используются предусловием, шагами или oracle текущего TC; validator подтверждает только минимальную проекцию и не заменяет эту смысловую проверку релевантности;
- provider/dictionary-bound значение целевой либо prerequisite-сущности, которого нет в подтверждённой materialization, или динамическую мутацию такой идентичности через `RUN-ID`;
- отсутствует поле `Требуется актуализация` для TC, основанного на применимом временном решении БА;
- требование получить fixture в TC;
- действие тестировщика, дублирующееся между предусловиями и шагами;
- подготовительное действие, которое выдаёт промежуточный результат за факт;
- `needs-test-data` без конкретных литералов и воспроизводимой подготовки либо `blocked-observability` в финальном runtime TC;
- `candidate-ui-calibration`, который не соответствует узкой политике из `test-design-profiles.md`;
- неисполняемый expected result или лишнее объединение независимых проверок.
- переход, изменение значения или счётчика, которое уже выполнено в предусловиях и поэтому не наблюдается в шагах;
- изменяющий состояние TC без source-backed восстановления или явного одноразового изолированного объекта;
- повторное заявление «одноразовый изолированный объект» для одинаковой identity tuple в нескольких TC; требуй разные конкретные ключи либо подтверждённый setup/reset-контракт;
- выдуманный cleanup: удаление, сброс, прямое изменение БД или иной способ, которого нет в источнике либо контракте среды;
- переход/предзаполнение без проверки конкретной идентичности объекта или ожидаемых литералов полей;
- шаг `Найти`, наведение, нажатие или другое действие над целевым объектом, который по oracle недоступен или невидим текущему актору в зафиксированном состоянии; достижимый поиск родительского объекта при проверке отсутствия дочернего элемента допустим;
- гибридное предусловие «установить/перевести объект в статус» без полного source-backed перехода: требуй либо декларативное исходное состояние конкретного объекта, либо отдельные исполнимые подготовительные действия;
- TC профиля `ролевой-доступ`, в котором учётная запись только подготовлена, но отсутствует явный вход пользователем требуемой роли перед целевыми шагами;
- отрицательный ролевой oracle «недоступно», если источник требует невидимость элемента, либо невидимость, если источник требует disabled-состояние;
- постусловие, которое сворачивает смену актора и действие в одну фразу или после нового входа не повторяет навигацию и поиск конкретного объекта;
- делегирующий шаг «Выполнить добавление/создание/редактирование/сценарий» вместо явных действий и значений текущего TC;
- нумерованный шаг или постусловие, в котором объединено несколько последовательных пользовательских действий либо действие и самостоятельная проверка;
- нажатие условно доступного контрола без обязательного UI-триггера из matrix/source непосредственно перед ним, включая предусловия и постусловия;
- поиск или декларативная подготовка произвольной записи по статусу/типу вместо identity tuple из тестовых данных; для дочернего объекта проверь также родительский контекст, если его ключ не доказан как глобально уникальный;
- UI-поиск по полю, которое не отображается в данной точке по source/matrix. Полный identity tuple должен доказывать подготовку объекта, но исполнимая команда поиска использует только видимые устойчивые признаки;
- неполный путь к вложенной сущности после входа или смены актора: должны быть исходный экран, поиск видимого родителя, переход в него и поиск ребёнка, если иной прямой маршрут не подтверждён source;
- обезличенный oracle видимости/отсутствия/открытия, который не содержит видимого литерала и не ссылается однозначно на ранее найденный объект;
- oracle предзаполнения формы редактирования без конкретных пар поле–ожидаемый литерал;

Не требуй отдельный отрицательный TC на отсутствие действия внутри объекта, если принятая matrix явно связывает это ограничение с более сильным source-backed результатом — объект целиком не виден тому же актору. Такой TC был бы неисполняемым; проверяй связанное покрытие, а не механическое число TC на каждую формулировку.

Не отклоняй измеряемый baseline `N` только потому, что это не литерал. Для проверки счётчика он допустим, если значение фиксируется до действия, действие описано полностью, а ожидаемый результат задаёт проверяемую дельту для того же показателя. Отклоняй непрозрачное действие или незафиксированный baseline, а не саму переменную.

Не требуй заранее известный литерал для значения, которое выдаёт сама система. Принимай source-backed property-check либо runtime binding с конкретными раздельными точками фиксации и сверки, идентичностью объекта и повторным использованием того же имени. Блокируй циклический oracle, который читает значение из проверяемого элемента и сравнивает тот же элемент с прочитанным значением без промежуточного перехода. Ссылка на внешний протокол без такого контракта остаётся дефектом. Если принятая matrix ошибочно требует недоступный фиксированный output, finding не может иметь `origin_stage: tc`.

Также проверь повторяющиеся ключи данных, корректность параметризации, сквозную нумерацию, группировку по функциональности и дубли по сигнатуре проверки. Вердикт: только `tc-accepted` или `tc-changes-required`. Принимать набор с material waiver нельзя.

Для каждого finding при `tc-changes-required` укажи `origin_stage` по `references/runtime/review-record.md`. Сравни дефект не только с ФТ, но и с принятой matrix: `matrix` допустим только когда проверенный TC уже корректен и после исправления matrix не требует изменения; `tc` — когда matrix достаточна, но writer неверно спроецировал её в TC; `both` — когда исправить нужно оба артефакта, включая случай, когда пропуск matrix уже привёл к пропуску покрытия в TC. Не помечай дефект как `matrix` только потому, что его первопричина находится выше по маршруту.

Первый TC review и manifest-driven `full` fallback являются полным проходом ограниченного artifact, а не fail-fast проверкой. Даже после первого material finding проверь каждый TC по всем обязательным gates, затем сгруппируй одинаковые дефекты и перечисли все затронутые TC. Перед verdict зафиксируй число проверенных TC. При `delta` проверь каждый изменённый TC и закрытие каждого прежнего finding; неизменные TC не перечитывай без зависимости. Не запускай второй проход только ради поиска замечаний, которые должны были войти в текущий объём.

В schema v2 review JSON запиши `artifact_index`, `semantic_input_hashes`, `reviewed_items` и `review_scope_complete: true` через штатный helper. Для полного TC review оба счётчика равны общему числу и в Markdown укажи `Проверено TC: N/N`; для delta `reviewed_tc_count` равен числу изменённых TC и укажи `Проверено изменённых TC: K/N`. Без этих полей итог невалиден и не передаётся controller-у.
